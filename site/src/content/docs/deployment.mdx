## Reference deployment: a single replica

The reference deployment is **one stateless server container plus
Postgres**. At one replica there is no cross-replica contention on Postgres's
`FOR UPDATE SKIP LOCKED` (the in-process worker pool still exercises it), so
scaling out to multiple replicas later is a deployment change, not a code
change — every piece of coordination (claims, guarded state transitions, the
sweeper) lives in the database, never in an in-process timer or queue whose
loss would change an outcome. Race-freedom under multiple replicas is proven
by the project's two-worker concurrency tests, not by running multiple
replicas in production.

## Running it

Build and run the container:

```sh
docker build -t slash-server .
docker run -p 8080:8080 \
  -e SLASH_DATABASE_URL_PATH=/run/secrets/database-url \
  -e SLASH_WEBHOOK_SECRET_PATH=/run/secrets/webhook-secret \
  -e SLASH_GITHUB_APP_ID=... \
  -e SLASH_GITHUB_PRIVATE_KEY_PATH=/run/secrets/github-app-key.pem \
  -v /path/to/your-database-url.txt:/run/secrets/database-url:ro \
  -v /path/to/your-webhook-secret.txt:/run/secrets/webhook-secret:ro \
  -v /path/to/your-app-key.pem:/run/secrets/github-app-key.pem:ro \
  slash-server
```

Or use `docker-compose.yml` in the repository root, which wires up Postgres
and the server together for local use — see the comments at its top for the
`.env` values it expects.

The server runs its own Postgres migrations at startup (`sqlx::migrate!`,
embedded in the binary at build time) and exits immediately if they fail, so
a bad migration never leaves the process half-started.

### Environment variables

| Variable | Required | Notes |
| ---------------------------------- | ---------- | ------- |
| `SLASH_DATABASE_URL_PATH` | yes | Path to a file containing the Postgres connection string. The file is read at startup and trimmed. |
| `SLASH_WEBHOOK_SECRET_PATH` | yes | Path to a file containing the webhook secret (matches the GitHub App's webhook secret). The server refuses to start without it — signature verification is never optional. |
| `SLASH_GITHUB_APP_ID` | yes | The GitHub App's numeric ID. |
| `SLASH_GITHUB_PRIVATE_KEY_PATH` | yes | Path to the App's private key **file** (not the key inline) — mount it read-only, mode `0400` if your platform supports setting it. |
| `SLASH_AUTH_SECRET` | yes | HMAC secret for signing user session cookies (account/team console). See the dual-path note below. |
| `SLASH_AUTH_SECRET_PATH` | no | Path to a file containing `SLASH_AUTH_SECRET` (trimmed), read instead of the inline env var. |
| `SLASH_WEB_DIR` | no | Root directory of the built web console SPA. Defaults to `web/dist` (relative to the server's working directory). |
| `RUST_LOG` | no | `tracing_subscriber` env-filter syntax, e.g. `info` or `slash_server=debug`. |

Each secret above also has an inline fallback (`SLASH_DATABASE_URL`,
`SLASH_WEBHOOK_SECRET`, `SLASH_AUTH_SECRET`) — but the file variants are
**strongly preferred** so secrets are never visible via `docker inspect` or
`ps aux`. If a `*_PATH` file is unreadable or empty, startup fails rather than
silently falling back. `SLASH_AUTH_SECRET_PATH` (the HMAC session secret)
follows the same rule; see `docs/user/onboarding` for it.

There is deliberately no way to pass the private key as an inline
environment variable — only a file path — and the config struct has no
`Debug`/`Display` implementation, so neither the webhook secret nor the
database URL (which may embed a password) can leak via a stray log line.

`SLASH_AUTH_SECRET` follows the same philosophy as the private key: prefer
`SLASH_AUTH_SECRET_PATH` so the session-signing secret lives in a mounted file
rather than the environment. When the file is set it takes precedence; the
inline `SLASH_AUTH_SECRET` is the fallback. As with the webhook secret, the
server refuses to start without a resolvable auth secret, and the secret is
never logged.

### Endpoints

| Endpoint         | Purpose |
|------------------|---------|
| `POST /webhook`  | The GitHub App's webhook URL. |
| `GET /healthz`   | Liveness check; always returns `200 ok` once the process is up. |
| `GET /metrics`   | Prometheus text-format metrics — see below. |

## Observability

`GET /metrics` exposes (see `crates/slash-server/src/metrics.rs`):

- `slash_webhook_deliveries_total{event,outcome}` and
  `slash_webhook_handler_seconds{outcome}` — webhook intake volume and
  latency.
- `slash_deliveries_pending` and `slash_deliveries_oldest_pending_age_seconds`
  — inbox depth and staleness; a nonzero, growing age means the worker pool
  is stuck or falling behind.
- `slash_invocations{status}` and
  `slash_invocations_max_dispatched_age_seconds` — how many invocations are
  in each lifecycle state, and how long the oldest one has been waiting in
  `dispatched` for a run id. A growing `dispatched` count or age is the
  stuck-invocation alarm; the sweeper resolves these automatically within its
  configured timeout, so a sustained climb points at GitHub API errors, not a
  logic bug.
- `slash_correlation_total{path}` — how each dispatch's run id was ultimately
  resolved: `dispatch_response` (the common case), `polled` (the sweeper's
  missing-run-id recovery), or `timeout` (never resolved). A healthy
  deployment is almost entirely `dispatch_response`.
- `slash_dispatch_failures_total{class}` — dispatches that ended in
  `dispatch_failed`, by failure class.

**Known gap** (see [known limitations](/limitations/)): there is no
`slash_github_api_calls_total`/rate-limit-remaining metric yet — GitHub API
call volume and remaining rate-limit budget are not currently observable
through `/metrics`. Watch application logs for `sweeper: failed to mint
token` / API error warnings as the interim signal.

## Key rotation

Rotating either credential requires no code change, only a config update and
restart:

- **Webhook secret**: generate a new secret, update it in the GitHub App's
  settings, then update `SLASH_WEBHOOK_SECRET` and restart the server. There
  is a brief window where GitHub may deliver with the old secret before the
  App settings save propagates — a handful of `401`s during that window are
  expected and harmless (GitHub retries deliveries).
- **Private key**: generate a new private key in the GitHub App's settings
  (this does not invalidate the old one immediately), roll out the new
  `.pem` file to `SLASH_GITHUB_PRIVATE_KEY_PATH` and restart, then delete the
  old private key from the App's settings once you've confirmed the new
  deployment is minting tokens successfully.

Do both periodically and always after any suspected credential exposure —
see the incident procedure below.

## Incident procedure

If the App is doing something it shouldn't (misbehaving on a repository,
credentials suspected leaked, or GitHub reports abuse):

1. **Stop the server process.** There is currently no per-installation or
   global kill switch (tracked as a known gap — see
  [known limitations](/limitations/)); stopping the process is the only way
   to immediately halt *all* dispatch activity across every installation.
   In-flight `claimed`/`dispatched` invocations are left durably in Postgres
   and will resolve themselves through the sweeper's normal timeout paths
   once the server restarts — nothing is lost by stopping it.
2. **If credentials are suspected compromised**: rotate the private key and
   the webhook secret immediately (above), and consider suspending or
   uninstalling the GitHub App from the affected repository/organization
   from GitHub's own UI — this immediately invalidates the App's ability to
   mint new installation tokens for it, independent of anything Slash itself
   does.
3. **Investigate** using the `invocations` table (a durable, append-mostly
   audit record of every dispatch attempt — installation, repo, PR, actor,
   command, workflow, and resulting run id, written *before* the dispatch API
   call) and the `/metrics` counters above.
4. **Resume** by restarting the server once the underlying issue is
   addressed. There is no separate "paused" state to clear — a stopped
   server simply isn't processing anything.

## Multi-tenancy notes

Installation tokens are minted per-repository with only the permissions a
given call actually needs, and cached separately per
`(installation_id, repository_id, permission_set)` — a token leak is bounded
to one repository and one permission set, not every repository the App is
installed on anywhere. On a `401`, the cached token is invalidated and
re-minted once.
