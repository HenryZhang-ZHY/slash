Command dispatch authorization runs through Slash's offline
[grants](/grants/) model: who may invoke a command is decided locally from the
`grants` table, deny-by-default, never by a live GitHub API lookup. This page
describes the model, the tier semantics, and the remaining gates around it.

## The two pieces

Every command declares a `permission` in its `.slash/*.yml` file: one of
`read`, `write`, or `admin` (default `write` if omitted). A grant (in the
application database) says who — a user or a team — may operate at which tier
on which command, repository, or organization.

At invocation time, Slash:

1. resolves the commenter to a Slash user and the repository to its
   organization,
2. loads the actor's grants (direct user grants plus their team grants),
3. and allows the dispatch only if the **highest allowed tier across matching
   grants is at or above** the command's declared `permission`.

See [Grants](/grants/) for the full model: scopes, deny-first semantics, and
fail-closed behavior.

## Why `read` exists but is rarely the floor

The `permission` tiers are `read`, `write`, and `admin`. A command that
dispatches a workflow runs code from the PR's head branch with your
repository's own secrets, so most commands are `write` or higher: only users
with push access can create branches in the repository at all, and allowing a
sub-write tier to invoke a command would silently undermine that trust
boundary — someone without push access could get their own branch's code
executed with your production credentials.

A `read`-tier command is meaningful only when it does *not* run head-branch
code with repository secrets. Choose the floor for each command deliberately:
the grant model makes the effective requirement explicit at a glance.

## Fail closed

If anything in the grant path doesn't cleanly resolve — a database error, an
unparseable grant row, a non-onboarded actor, or an unresolvable
organization — the command is **denied**, unconditionally. There is no
fallback to any other authorization source: missing grant, error, and explicit
deny are all the same verdict.

## What forks change

Fork PRs are not supported (see [known limitations](/limitations/)):
`workflow_dispatch` cannot target a ref on a fork, so there is nothing to
dispatch even if grant resolution succeeds. Slash detects this and comments
once per PR rather than silently doing nothing.

## Re-running

Clicking **Re-run** on a check run re-resolves the *rerequester's* current
grant — not the original invoker's — against the command's *current*
configuration. A user whose grant has since been downgraded or removed gets a
denial on the check run itself, with no new comment; a re-run is never a way
to bypass the original gate.

## History: the pre-grant collaborator-role model

Before grants, authorization compared the commenter's GitHub repository role
against the command's `permission`. It is retained here only for context.

The old gate resolved the commenter's role via
`GET /repos/{owner}/{repo}/collaborators/{username}/permission`, reading the
response's `role_name` field specifically — not the top-level `permission`
field, which collapses `maintain` into `write` and `triage` into `read` and
would otherwise make a `maintain`-gated command passable by plain write access.
The gate then dispatched only if the actual role was **at or above** the
command's declared level. The old tiers were `write | maintain | admin`;
`read` and `triage` were rejected entirely, because a dispatching command runs
head-branch workflow code with repository secrets. In this model, `write` was
the floor — the current `read` tier did not exist.

The old model also failed closed: any non-success outcome — a 5xx, 403, 404,
timeout, or unparseable role — was a **deny**, with at most a best-effort 😕
reaction and never a comment, since a resolution failure meant the commenter's
trust level was genuinely unknown. That fail-closed principle carries forward
unchanged into the grants model.
