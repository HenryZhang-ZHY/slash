Test Engine 把 Slash 控制面变成一个测试治理闭环：收集你 CI 的测试结果，从执行
历史中检测 flaky 测试，并自动**隔离（quarantine）**它们，让它们不再阻塞 PR。它
遵循 Buildkite Test Engine 模型：归一化结果 → 检测 flakiness → 在后续运行中
soft-fail 或跳过已隔离的测试。

Slash 仍然是控制面 —— 它绝不运行你的测试。执行发生在你自己的 CI 上；Slash 负责
收集、归一化和处置。

## 数据模型

测试结果构成四级层级：

- **Suite（套件）** —— 一组命名的测试集合，由 `(owner, repo, suite_key)` 标识。
  第一次上传落地后套件即存在。
- **Test（测试）** —— 套件内一个命名的测试。它带有可变的 state（`enabled` /
  `muted` / `skipped`）、labels 和 owner team 引用。
- **Run（运行）** —— 产生一批执行结果的一次 CI 调用，由 `(ci_provider, run_ref)`
  标识。run 可能来自 slash 命令的 GitHub Actions workflow，也可能来自任何其他 CI
  系统。
- **Execution（执行）** —— 一次运行中一个测试的观测结果：状态、时长、堆栈和捕获
  时间。执行一旦记录就是 append-only。

### 测试状态

| 状态 | 含义 |
| --- | --- |
| `enabled` | 正常运行。失败会使 PR 失败。 |
| `muted` | **Soft-fail** —— 测试仍然运行并记录元数据，但失败不再使 PR 失败。这是自动隔离的处置方式。 |
| `skipped` | 完全不再运行。保留给手动或硬性成本控制决策；检测器绝不自动 skip。 |

## Flaky 检测

当一个测试在滚动 **7 天窗口**内满足以下条件时，被判为 **flaky**：

- 至少 **3 次执行**（防止小样本误报的分母），并且
- 观测到 **先失败后通过的恢复** —— 窗口内一次失败或错误之后跟着一次通过。

检测是一个对持久化执行记录**层级触发的 reconcile（对账）**，而不是事件处理器：
sweeper 在它的常规心跳上对 `tests` 表做有界游标扫描。它是幂等的，所以一次崩溃的
pass 会在下一个间隔重跑。转换是受保护的 compare-and-swap 更新，所以手动状态编辑
和自动 reconcile 永远不会破坏性地竞争。

两个转换自动发生：

- **enabled → muted** —— 当测试 flaky 时。它继续运行（这样检测器能继续观测它），
  但不再使 PR 失败。
- **muted → enabled** —— 当窗口滚过失败、测试稳定（近期无失败）时。单次 flake
  不会自动重新 mute；7 天窗口必须再次显示恢复。

`skipped` 测试永远不会被自动解除隔离 —— skip 会产生零执行数据，会永久弄瞎检测器，
所以它始终是手动决策。

## 处置闭环（接入 CI）

端到端闭环是：**运行测试 → 上传结果 → 检查隔离 → 跳过/soft-fail 已隔离测试**。
一个 slash 命令的 workflow 用三步来执行它：

1. **先检查隔离。** 用你的 collection token 调用 `GET /v1/test-engine/quarantined`；
   它返回当前状态为 `muted` 或 `skipped` 的测试名。
2. **运行你的测试**，完成后把结果上传到 `POST /v1/test-engine/upload`（或 `/cargo`
   与 `/vitest` 变体）。
3. **应用处置。** 对已在隔离列表中的测试，soft-fail 或跳过它，而不是让 PR 失败。

slash 仓库里的
[`fake-ci-test-flaky` 命令](https://github.com/HenryZhang-ZHY/slash/tree/main/.slash/fake-ci-test-flaky.yml)
就是这个闭环的可直接接入模板。它运行一个确定性地 flaky 的测试（奇数 run number
失败、偶数通过），上传结果，查询隔离列表，并在检测器把测试 muted 后报告 `neutral`
结论。它需要你的部署提供三块配置：

| 配置 | 示例值 |
| --- | --- |
| 上传端点（`vars`） | `https://slash.example.com/v1/test-engine/upload` |
| 隔离查询端点（`vars`） | `https://slash.example.com/v1/test-engine/quarantined` |
| Collection token（`secrets`） | 管理 API 签发的按套件 bearer token |

## Collection tokens

每次上传和隔离查询都由一个**按套件的 collection token** 认证 —— 一个限定到单个
套件（而非整个 installation）的 bearer secret：

```http
Authorization: Bearer collection-token-value
```

token 通过 [Test Engine 管理 API](/zh/api/test-engine/) 签发。token 决定目标套件；
上传体里从不携带套件 ID。token 可以随时吊销，吊销后立刻停止对 ingestion 请求的
认证。

## 支持的格式

ingestion 端点接受三种形状（完整 schema 见
[ingestion API](/zh/api/ingestion/)）：

| 端点 | 格式 |
| --- | --- |
| `POST /v1/test-engine/upload` | 归一化 JSON，或带 XML `Content-Type` 的 JUnit XML |
| `POST /v1/test-engine/upload/cargo` | 换行分隔的 Cargo libtest JSON 事件 |
| `POST /v1/test-engine/upload/vitest` | Vitest 结果（数组，或 `{ "tests": [...] }`） |

CI provider 会被记录，但与下游逻辑无关 —— slash 同样轻松地归一化非 Buildkite CI。
