# Slash 1.0 — Test Engine (Test Governance) Design

Status: **Draft for review.** Revision 2 (2026-08-11) incorporates the PR #2
review (disposition default → `muted`, M1 collector pinned to server endpoint,
`owners[].team_id` aligned with the org/user lane, tightened flaky window).

This document is the design for slash's Test Engine lane in the 1.0 release. It
is a companion to [`0.0.1-spec.md`](./0.0.1-spec.md) and follows its conventions
(English working language, durable-record state model, per-milestone exit
criteria). The 1.0 strategy is Henry's: test results → collect/normalize →
flaky auto-detect + quarantine → cross-agent split/retry → event-driven
governance rules + agent-facing API, **as small and as fast as possible and as
close to Buildkite Test Engine as reasonable** — "极可能抄 Buildkite".

The source of truth for the layered model is the Buildkite Test Engine
distillation in Cindy's notes
(`/home/nm/.slock/agents/21e3948a-8ade-4cc3-b555-91ad4bf19e57/notes/buildkite-test-engine.md`),
which maps the Buildkite concept space onto slash's shape. The key observation
behind this design:

> **Test Engine shape == slash shape.** Buildkite Test Engine is a managed
> test-results control plane that ingests + normalizes + analyzes + auto-disposes
> (especially flaky), with a declarative workflow-actions layer and an
> agent-facing MCP server. Slash is already a managed control plane with a
> declarative `.slash/*.yml` command model and a check-run lifecycle. So slash's
> Test Engine is the *test-results → auto-dispose(quarantine/notify)* capability
> expressed as slash-declarable commands and an ingestible data plane — not a
> parallel system.

## 1. Problem Statement

slash commands (`/deploy`, `/test`, `/fake-ci-test-pass`) trigger workflows whose
jobs run tests. Today slash knows an invocation ran and whether its check run
succeeded or failed (**§6.2 conclusion**), but it knows **nothing about the
tests** inside: which tests ran, which passed/failed, which are flaky, how long
they took, who owns them. Consequences:

- A flaky test fails intermittently and **blocks PRs** on branch protection —
  the exact pain Buildkite Test Engine exists to solve.
- Failure is all-or-nothing at the check-run level; there is no
  per-test signal, no history, no quarantine.
- Test workload is not distributed across parallel lanes; there is no
  split/retry on failure.
- There is no governance surface for *test-level* state (mute/skip/quarantine)
  or reliability monitoring.

The goal of the slash Test Engine is to make the test-results → auto-dispose
loop a first-class, slash-declarable capability spanning every CI slash drives,
not just a hand-rolled analytics sidebar.

## 2. Non-goals for 1.0 (the slimmer the faster)

- **Running tests.** Slash is a control plane that *drives* workflows; execution
  happens on the tenant's CI runners. Same boundary as 0.0.1 (spec §2.4).
- **A general-purpose analytics/dashboard.** Surfacing slowest/least-reliable
  per suite and saved views are future roadmap, not 1.0.
- **A full agent-facing MCP server.** 1.0 exposes a minimal, typed
  agent-callable management API over the existing command/HTTP surface; a
  dedicated MCP server is post-1.0.
- **Supporting every test framework's native output.** 1.0 ingests a small set
  of normalized result formats (JUnit XML + a raw JSON upload), which covers the
  frameworks Buildkite collectors already normalize to.
- **Fork-PR test ingestion, org-level defaults, billing.** Deferred, matching
  spec §2.4.

## 3. Data Model — the durable record

The state model follows spec §7.2's rule: a **durable record plus
level-triggered reconciliation**. Test results are events from CI; slash
normalizes them into a durable Postgres record and reconciles derived state
(quarantine, notifications) from that record, never from the events directly.

Concept hierarchy (Buildkite's suite → tests → runs → executions):

- **Test Suite** — a named collection of tests, identified by
  `(installation_id, owner, repo, suite_key)`. Established on first execution
  upload.
- **Test** — a single named test within a suite:
  `(suite_id, name, file/line, label[], owner_team_ids)`. `owner_team_ids`
  (`UUID[]`, the proposed `owners[].team_id` set) is deferred in 1.0 (see §8
  Q3) but keeps the slot referencing the org/user lane's team schema (`teams.id`
  UUID), so the two lanes stay in sync.
- **Execution** — one observed result of a test:
  `(test_id, run_id, status, duration_ms, stack, captured_at)`. Immutable
  append-only once recorded.
- **Run** — one CI invocation that produced a batch of executions:
  `(invocation_id, run_ref, ci_provider, started_at, finished_at)`.
  A run may be a slash-commanded GH Actions workflow run, or a collection
  upload from a non-slash CI (e.g. the repo's own Buildkite pipeline).

`state` on a Test holds the current disposition:

| state     | meaning                                    |
|-----------|--------------------------------------------|
| `enabled` | run normally                               |
| `muted`   | softfail: still run, failures don't fail   |
| `skipped` | not run (bktec-style skip of quarantined)  |

**Flaky detection** derives from repeated executions: a test that fails on some
executions of the same declared input and passes on others within a
config window is a candidate (Buildkite's automatic flaky detection + quarantine;
label removal when it stops flaking). Detection is a reconcile pass over durable
execution history — event-driven, not a cron, and idempotent under redelivery.

### 3.1 Storage design

New tables (extending spec §7.2's schema, all Postgres via sqlx):

| table            | notes                                                     |
|------------------|-----------------------------------------------------------|
| `test_suites`    | `(installation_id, owner, repo, suite_key)` UNIQUE         |
| `tests`          | `(suite_id, name)` UNIQUE; mutable `state`, `label[]`, `owner_team_ids UUID[]` |
| `test_executions`| append-only; FK test_id/run_id; status, duration_ms, stack |
| `test_runs`      | UNIQUE on `(installation_id, ci_provider, run_ref)`; `ci_provider` in the key disambiguates the same `run_ref` across CI providers |

Every transition on `tests.state` is a **guarded compare-and-swap**
(`UPDATE ... WHERE user_id = $1 AND state IN (...)`), same discipline as spec
§7.2, so manual state changes, flaky auto-quarantine, and un-quarantine never
race destructively. Retention: executions purged after 120 days (Buildkite
parity); non-terminal reconcile work is never dropped by age alone.

## 4. Ingestion / normalization

Reuses what already exists rather than building collectors from scratch:

- The repo's own Buildkite pipeline (`pipeline.yml` + `buildkite-test-collector`
  in `Dockerfile.ci`) already uploads slash's test results to Buildkite Test
  Engine — that is the **live dogfood of the collection layer**, and 1.0 keeps it
  as a reference ingestion path.
- slash-commanded GH Actions runs produce JUnit XML / raw JSON that a *thin
  collector* (a helper the workflow emits, or a `slash` server upload endpoint)
  normalizes and posts to slash's own ingestion endpoint.

Normalization contract: a small fixed schema (suite, test, execution fields
above). CI provider is recorded (and participates in the `test_runs` unique
key, §3.1) but irrelevant to downstream logic — slash normalizes non-Buildkite
CI too (Buildkite Test Engine parity).

**M1 collector form is pinned to the server-side upload endpoint.** A slash-
commanded test workflow POSTs its normalized results (raw JSON / JUnit XML) to
the server's ingestion endpoint, authenticated by a per-suite collection token.
A compiled `bktec`-style client binary is deferred — it has no consumer in 1.0
and adds build/distribute/sign/OIDC burden M1 does not need; revisit it only
for offline runners or workflows that cannot reach slash's HTTP endpoint.

Auth: collection uploads carry a per-suite collection token issued by slash
(Buildkite `TEST_ENGINE_*` env parity); the token is scoped to one suite, not the
installation.

## 5. The 1.0 thin slice (M1)

Following Cindy's and the 0.0.1 plan's "thin slice first" lesson, 1.0 does **not**
lay out all five layers at once. **M1 is the minimal closed loop that dogfoods
end-to-end on the slash repo itself:**

> **flaky detection → auto-quarantine → bktec-style skip/mute on subsequent runs.**

Concretely M1 builds, in this order:

1. Ingestion endpoint: the server-side raw-JSON/JUnit upload + durable
   `test_executions` storage (§3), so real executions land in Postgres.
2. Flaky detector: a reconcile pass that, from the repo's own collected
   executions, marks a test `muted` (default disposition, §8 Q1) with the §3.1
   CAS guard, and un-quarantines (label removal) when it stabilizes.
3. Disposal hook: a slash-commanded test workflow calls the server endpoint to
   **soft-fail/skip already-quarantined tests** (the bktec client behavior:
   "skip/mute flaky tests"), so quarantined tests stop failing PRs.

**Flaky detection threshold (M1, tightened per review):** a test is flaky iff,
for the **same declared input**, over a **rolling 7-day window** with **≥3
executions** (a denominator that guards against small-sample false positives),
there is an observed **fail-then-pass recovery**. Detection is a level-triggered
reconcile over durable executions — event-driven, never a cron — and the
transition is a guarded CAS (§3.1), so manual state, auto-quarantine, and
un-quarantine never race. Un-quarantine fires when the window rolls past the
failures and the test stays green.

Because there is no real flaky test in M1's own suite, a **deterministic fake-
flaky fixture** (`fake-ci-*` command emitting a scripted fail-then-pass,
exercising the dogfood path) is a hard M1 requirement — without it the flaky
path is untestable until a genuine flake appears.

**Dogfood:** drive the loop on the slash repo's own suite of `fake-ci-test-*`
commands + BDD fixtures (`docs/bdd/*.feature`) so a real invocation exercises
ingest → flaky-mark → skip on a real PR. A quarantine "from fake flakiness"
fixture stands in for a real flaky test until a genuine one is observed.

M1 exit: a throttled set of slash repo's synthetic executions ends up quarantined
and then skipped on the next invocation — measured, not asserted; the `tests`
table, `test_runs`, and `test_executions` tables exist with their constraints and
CAS transitions; the ingest + skip loop is covered by Postgres-backed integration
tests gated on `SLASH_TEST_DATABASE_URL`.

## 6. Horizontal expansion (M2–M3)

Once M1's loop is green and dogfooded, expand without rebuilding:

- **M2 — full ingestion/normalization**: JUnit XML + raw JSON normalization
  across frameworks; non-slash CI collectors; per-suite collection tokens and
  upload-health observability (Buildkite "*upload health*" parity).
- **M3 — governance + agent-facing API**: event-driven workflow/monitor
  (duration-threshold, reliability monitors → `alarm`/`recover`) driving
  actions (label / state / Slack); and a minimal, typed, slash-declarable
  management API so agents can `list_test_runs` / `get_failed_executions`
  (with stack) / set `state` — the seed of the post-1.0 MCP server.

Each milestone ends green CI with its exit criteria met before the next, and each
new capability is dogfooded on the slash repo before it is considered done.

## 7. Engineering conventions (inherit spec §9)

- English working language; rustfmt + `clippy -D warnings`; conventional commits.
- The upload surface takes untrusted bodies: no panic reachable from them
  (explicit size limits at the edge, property/fuzz tests, panic-guarded handlers)
  — spec §9.
- Persistence Postgres-only via sqlx; state-transition disciplines of §7.2
  (guarded CAS, terminal-state absorption, level-triggered reconcile).
- Reuse `.slash/*.yml` command model / `slash-config` / `slash-core` permission
  rather than building a parallel mechanism (spec §5.2 fail-closed applies to
  any test-governance command that mutates state).
- No-database CI still runs pure-crate unit tests; Postgres-backed tests gate on
  `SLASH_TEST_DATABASE_URL`.

## 8. Review decisions (2026-08-11, Cindy review on PR #2, non-blocking)

1. **Default disposition is `muted`, not `skipped`.** Buildkite flags Mute as
   recommended: a muted test still runs and records metadata, so auto
   un-quarantine can observe when it recovers; `skipped` produces zero data and
   would permanently blind the detector. `skipped` is reserved for manual or
   hard-cost-control scenarios, never the auto default. Applies to §3 state and
   §5 M1.
2. **M1 collector = server-side ingestion endpoint.** A compiled `bktec`-style
   binary is deferred until there is a real need (offline runner, or a workflow
   that cannot reach slash's HTTP endpoint). §4 now pins this.
3. **Ownership deferred**, but `owner_team_ids UUID[]` (null-able array of team
   uuids, the future `owners[].team_id`) references the org/user lane's team
   schema — `team.id`(uuid) + org-unique `team.slug` + `team.organization_id`
   (agreed with @SlashOrg) — so lanes stay aligned and the slot backfills
   cleanly. 1.0 mutes by suite/test name.
4. **Detection window tightened** to: same input, rolling 7-day window, ≥3
   executions, observed fail-then-pass recovery (level-triggered reconcile,
   guarded CAS). Includes a deterministic fake-flaky fixture in M1 (hard
   requirement). Now in §5.

Remaining open for final sign-off: whether Henry wants `muted` (standing
recommendation, already adopted) or any adjustment to the M1 window. Otherwise the
design proceeds to task breakdown.
