# Slash 0.0.1 — Product & Technical Specification

Status: Draft, agreed for implementation
Date: 2026-08-03 (revision 3)
Revision 2 incorporates the design review in [`0.0.1-design-review.md`](./0.0.1-design-review.md):
`workflow_dispatch` now returns run IDs (§6.3 rewritten), GitHub platform facts corrected
(§4.1, §5.1, §5.2, §7.4), the trust model tightened (§3, §4.1, §5.2), and the runtime moved
from purely event-driven to a durable-record + reconcile design (§7.2, §7.3).
Revision 3 records the persistence decision — PostgreSQL from day one; a no-database
0.0.1 and a SQLite-first 0.0.1 were evaluated and rejected (§7.1) — scopes the 0.0.1
reference deployment to a single replica (§7.1, §10), and reclassifies the §6.3 polling
fallback as the required resolver for ambiguous dispatch outcomes rather than insurance.
It also completes the invocation lifecycle — a `claimed` state that precedes all side
effects, `dispatched` written ahead of the POST, a terminal `aborted` state, and the 72h
deadline resolving to `completed`/`timed_out` (§5, §7.2) — and unifies the feedback for a
failed permission resolution: deny, 😕 reaction at most, never a comment (§5, §5.2, §6.4).
Invocations are keyed by `(installation_id, comment_id, attempt)` so a re-run claims a
fresh row instead of colliding with the terminal original (§6.5, §7.2).

## 1. Problem Statement

GitHub Actions has poor UX for comment-driven CI ("ChatOps"). The natural way to
trigger a task from a PR is to type a slash command into the PR comment box, but
the corresponding trigger event (`issue_comment`) runs the workflow from the
**default branch**, detached from the PR. Consequences:

- The workflow run is not associated with the PR head SHA, so its status never
  appears in the PR checks section and cannot be used as a required status check.
- Workarounds (e.g. submitting a `pull_request_review` of type "comment" whose
  body equals the command) force users through extra, unintuitive UI steps.
- Community solutions ([peter-evans/slash-command-dispatch]) are themselves
  GitHub Actions running on `issue_comment`, so they inherit the same problems
  and require per-repository dispatcher workflows and PAT plumbing.

Prow (Kubernetes) proves the UX (`/retest`, `/lgtm`, argument-carrying commands)
but requires a self-hosted Kubernetes deployment and runs jobs on its own
infrastructure rather than GitHub Actions.

[peter-evans/slash-command-dispatch]: https://github.com/peter-evans/slash-command-dispatch

## 2. Product Definition

**Slash** is a multi-tenant SaaS delivered as a **GitHub App**. It is a pure
control plane: it receives webhooks, interprets slash commands from PR comments,
triggers the user's own GitHub Actions workflows, and mirrors their execution
state back onto the PR via the Checks API.

The execution plane is the user's existing GitHub Actions runners — users deploy
nothing (Buildkite's control-plane/execution-plane split, minus the agent).

**Target segment for 0.0.1: teams whose pull requests come from branches in the
same repository** (private and org repositories). Fork PRs are not supported
(§2.4, §11) because `workflow_dispatch` cannot target a ref in a fork.

### 2.1 User experience

1. Install the Slash GitHub App on a repository (or org).
2. Commit command definitions as YAML files under `.slash/` on the default branch.
3. Comment `/deploy staging --timeout=30m` on any pull request.
4. Slash reacts 🚀 on the comment, creates a check run `slash/deploy` on the PR
   head SHA, dispatches the mapped workflow, and updates the check run live
   (`queued` → `in_progress` → `completed`) with a link to the run.
5. Re-running is a click: GitHub renders a "Re-run" button on the check run, and
   Slash re-dispatches the stored invocation (§6.5).
6. Because status arrives via the Checks API, `slash/<command>` can be marked as
   a required status check via normal branch protection settings — **with the
   caveats in §6.6, which are a footgun if not understood.**

### 2.2 Design principles

- Minimum resources, maximum tenants, maximum stability. Rust; small durable core.
- Convention over configuration; sensible defaults; errors reported to the user
  in the PR, never silently dropped — *except* where reporting would let an
  unprivileged user turn one comment into bot spam (§6.4).
- One command maps to exactly one workflow (0.0.1 simplification).
- Every state that can be waited on has a timeout, and every timeout is driven
  from durable state, not from process memory (§7.3).

### 2.3 Goals (0.0.1)

- Slash command parsing from PR comments (positional + key-value arguments).
- Command definitions in `.slash/*.yml`, read from the default branch.
- Trigger `workflow_dispatch` on the PR head branch.
- Full check-run lifecycle synced to the PR head SHA.
- Permission gating and argument validation with user-visible error feedback.
- Re-run via the check run's native "Re-run" button (`check_run.rerequested`).
- A `slash validate` CLI so tenants can check `.slash/` in their own CI.

### 2.4 Non-goals (0.0.1)

- Fork PRs (`workflow_dispatch` cannot target a fork ref). Commands on fork PRs
  get a polite explanatory comment and no dispatch (§6.4, §11).
- Multiple workflows per command; command aliases; built-in chat commands
  (`/retest`, `/help` as *typed commands* — re-run is delivered via §6.5 instead).
- Automatic re-trigger on `pull_request.synchronize` (§6.6, §11).
- Server-side validation of `.slash/` on push (the `slash validate` CLI covers
  the need for 0.0.1; see §11).
- GitHub Enterprise Server; SCMs other than github.com.
- Merge queue, `/lgtm`-style review automation, OWNERS files.
- Web dashboard, billing, org-level config inheritance.

## 3. Command Grammar

Only the **first line** of a comment is parsed. It must start with `/` followed
by a command name.

```
/deploy staging --force --timeout=30m --reason="hot fix"
 ^cmd   ^positional  ^bool flag  ^key=value    ^quoted value
```

Grammar (POSIX-like):

- Command name: `/[a-z][a-z0-9-]*`, matched case-insensitively (the input is
  lowercased before lookup) and terminated by whitespace or end of line.
- Positional arguments: bare tokens, bound in order to `args` entries that are
  not given as `--key` form.
- Key-value: `--key=value` or `--key value`.
- Boolean flags: bare `--flag` binds the string `"true"`.
- Quoting: double quotes group tokens containing spaces; `\"` escapes a quote.
- All values are strings (matching `workflow_dispatch` input semantics).

### 3.1 Rejected input

- Comments not starting with `/` are ignored (zero cost path).
- Comment `edited` and `deleted` actions are ignored; only `created`.
- Comments authored by bots (including Slash itself) are ignored.
- Keys beginning with `slash_` are rejected with a usage error: the `slash_`
  prefix is reserved for the inputs Slash injects (§4.2). This is a hard rule,
  not a convention — see §5.4.
- A value must match `^[A-Za-z0-9._@:/+=,-]{0,256}$` unless its `args` entry sets
  `free_text: true` (§4.1). Rationale: values flow into `workflow_dispatch`
  inputs, and tenant workflows that interpolate `${{ inputs.x }}` inside `run:`
  would otherwise be script-injectable by anyone who can pass the permission
  gate. Slash makes that path a feature, so Slash carries the mitigation.

### 3.2 Commands not on the first line

`/deploy staging` on the third line of a comment is **not** executed. To avoid
silently dropping what the user clearly intended (§2.2), Slash scans the
remaining lines for `^/<name>` where `<name>` is a **configured command** of that
repository; on a match it replies once with "commands must be on the first line
of a comment" and reacts 😕. Matching only configured names is what makes this
safe from the false-positive problem described in §6.4. The reply is itself
subject to the §6.4 rules: posted only when the author's permission resolves to
at least `read` (a failed resolution gets at most the 😕 reaction, §5.2), and at
most once per PR.

This is a deliberate divergence from Prow, which matches commands on any line
(`(?mi)^/cmd...`) and pays for it with code-block stripping, HTML-comment
stripping, and per-plugin deduplication — and still misfires inside fenced code
blocks. First-line-only eliminates that class at zero cost.

## 4. Configuration: `.slash/`

- Location: `.slash/*.yml` (also `.yaml`) at the repository root.
- **Always read from the default branch**, never from the PR branch. This
  prevents "pwn request" attacks where a PR modifies command definitions to
  escalate through the App's permissions.
- One command per file. The `command` field is authoritative; the filename is
  irrelevant. Duplicate command names across files are a configuration error
  (reported when a command is invoked, naming both conflicting files).
- Parsed configuration is cached keyed by `(owner, repo, default-branch head SHA)`
  — never by branch name, so the cache cannot go stale: a new default-branch
  head is a new key, and old keys are simply evicted.

Note the deliberate asymmetry with §5.1: the *policy* (who may invoke a command,
which workflow file, which arguments) comes from the default branch and cannot be
changed by the PR under test; the *executed workflow body* comes from the PR head
branch. A write-access user's PR can therefore change what `/deploy` **does**,
but not **who may invoke it**.

### 4.1 Schema

```yaml
# .slash/deploy.yml
command: deploy                  # required; unique per repo
description: Deploy the PR to an environment   # optional; shown in errors
permission: write                # optional; default: write
                                 # one of: write | maintain | admin
workflow: deploy.yml             # required; file under .github/workflows/
                                 # must exist on the DEFAULT branch and
                                 # declare `on: workflow_dispatch` (§5.1)
args:                            # optional; ordered list
  - name: env                    # required per entry
    description: Target environment
    required: true               # default: false
    choices: [staging, production]   # optional enum
  - name: timeout
    default: "15m"               # optional; used when not provided
  - name: reason
    free_text: true              # relaxes the value charset of §3.1
```

Validation rules (all enforced by `slash-config`, all covered by
`slash validate`):

- Unknown top-level or arg-level keys → configuration error.
- `command` must match `/[a-z][a-z0-9-]*` minus the reserved names `help` and
  `slash` (reserved for future built-ins).
- `permission` must be one of `write | maintain | admin`. **`read` and `triage`
  are rejected.** Rationale: a dispatching command grants the ability to run
  head-branch workflow code with the repository's secrets; allowing sub-write
  invocation would silently void the trust argument in §5.1. (Note that GitHub's
  own permission API collapses triage into read — see §5.2 — so those tiers were
  never faithfully expressible anyway.)
- `workflow` must match `^[A-Za-z0-9._-]{1,100}\.(ya?ml)$` — no `/`, `\`, `%` or
  `..`. It is interpolated into an API path and must be percent-encoded there.
- `args[].name` must match `^[a-z][a-z0-9_-]*$` and must **not** start with
  `slash_` (§4.2), and must be unique within the command.
- `required: true` entries must precede optional entries in positional binding.
- `default` is rejected on a `required: true` entry (it could never be used),
  and a `default` value must itself satisfy the entry's `choices` and the §3.1
  value rules (with the same `free_text` opt-out).
- Total inputs (user args + injected inputs) must not exceed the
  `workflow_dispatch` limit of **25** top-level properties; the serialized
  `inputs` payload must not exceed 65,535 characters (validated at invocation
  time, when values are known).
- Resource limits on the directory as a whole: at most 50 files, at most 256 KiB
  total, at most 32 levels of YAML nesting, YAML aliases/anchors disabled. A
  configuration exceeding these is a configuration error, not a parse hang: this
  YAML is attacker-influenced input to a shared multi-tenant process.

### 4.2 Injected workflow inputs

Slash injects the following inputs. They are **sent only if the target workflow
declares them**, so adding a new injected input is never a breaking change for
tenants and no tenant is forced to declare inputs they do not use.

| Input              | Value                                                  |
|--------------------|--------------------------------------------------------|
| `slash_run_id`     | UUID v4 generated per invocation (logging/correlation) |
| `slash_pr_number`  | PR number                                              |
| `slash_head_sha`   | PR head SHA at invocation time                          |
| `slash_actor`      | Verified login of the comment author                    |
| `slash_actor_id`   | Numeric user ID of the comment author (rename-stable)   |

`slash_actor`/`slash_actor_id` exist because the dispatch is performed with the
App's installation token, so `github.actor` inside the run is `slash[bot]`.
Workflows needing identity-based logic **must** use `inputs.slash_actor_id`, and
tenants get a real audit trail instead of "slash[bot] deployed to production".

To decide what to send, Slash fetches `.github/workflows/<workflow>` **at the PR
head ref** (the version that will run) and parses its
`on.workflow_dispatch.inputs` keys. This also lets Slash pre-validate that every
configured arg is declared, converting GitHub's opaque HTTP 422 into a precise
error message before dispatch. If the file cannot be fetched or parsed, Slash
sends all injected inputs and surfaces any resulting 422 verbatim.

Example user workflow — note that no `run-name` is required (see §6.3), and that
inputs reach `run:` via `env:`, never through `${{ }}` interpolation:

```yaml
# .github/workflows/deploy.yml
name: deploy
on:
  workflow_dispatch:
    inputs:
      slash_head_sha: { required: false }
      slash_actor: { required: false }
      env: { required: true }
      timeout: { required: false, default: "15m" }
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ inputs.slash_head_sha }}   # the SHA the check run reports on
      - name: Deploy
        env:
          TARGET: ${{ inputs.env }}           # via env, NOT inline in run:
          ACTOR: ${{ inputs.slash_actor }}
        run: ./deploy.sh "$TARGET" "$ACTOR"
```

## 5. End-to-End Flow

Guards are ordered so that **cheap syntactic checks and the trust gate come
before any user-visible side effect**, with one sanctioned exception: the
best-effort, budget-capped 😕 reaction on a failed permission resolution
(§5.2, §6.4). An unprivileged commenter must not be able to make Slash post
comments or spend unbounded API budget (§6.4).

```
issue_comment(created)
  → is PR? not bot? first line starts with "/"?          (else: the §3.2 scan for
                                                          misplaced commands,
                                                          otherwise ignore silently)
  → resolve author permission (§5.2)                     (resolution error → deny:
                                                          😕 reaction at most, no
                                                          comment (§5.2))
  → GET the pull request                                 (issue_comment carries no head info)
      → state == "open"?                                 (else comment: PR is not open)
      → head.repo.id == base.repo.id?                    (else comment: forks unsupported, once per PR)
  → load .slash/ from default branch (cached by SHA)     (config error → comment + 😕)
  → match command                                        (unknown → §6.4 rules)
  → author permission ≥ command's permission             (denied → comment + 😕)
  → parse & validate args (§3.1, §4.1)                   (invalid → usage comment + 😕)
  → claim invocation row, status=claimed, attempt=1:
        UNIQUE(installation_id, comment_id, attempt)
        already present and past claimed → stop (duplicate; later states are
        owned by workflow_run events and the sweeper)
        already present in claimed → resume it: every pre-dispatch step
        below is idempotent (§6.1)
  → react 🚀 on the comment
  → create check run "slash/<command>" on head SHA, status=queued
      store check_run_id on the invocation row
  → supersede older non-terminal invocations of (repo, pr, command) (§6.7)
  → re-read the branch tip; differs from captured head SHA?
        → comment: "the PR head moved, re-issue the command", abort (§8)
  → mark status=dispatched (write-ahead, BEFORE the POST; §7.2), then
    POST workflow_dispatch (ref = refs/heads/<head branch>,
                            inputs = args then injected (§5.4))
      → 2xx: store workflow_run_id from the response, status=correlated (§6.3)
      → permanent failure (404/422): status=dispatch_failed, check run
        completed/failure with detail
      → ambiguous failure (timeout/5xx): stays dispatched, let the sweeper
        resolve it — never blindly re-POST (§7.6)

workflow_run(requested|in_progress|completed) webhook
  → look up invocation by workflow_run_id (exact; §6.3)
  → guarded state transition (§7.2); non-monotonic or duplicate events dropped
  → update check run per §6.2

check_run(rerequested) webhook
  → re-run the stored invocation (§6.5)

sweeper (every replica, on an interval; §7.3)
  → invocations stuck in `claimed` past 60s           → crashed before the POST
                                                         (§7.2): mark aborted,
                                                         which completes its
                                                         check run — found by
                                                         stored id or head-SHA
                                                         lookup (§6.1)
  → invocations stuck in `dispatched` past 60s        → start polling for the
                                                         run id; give up at
                                                         10 min (§6.3)
  → invocations in `correlated` past the run deadline → poll, then time out
  → check-run updates that previously failed          → retry
  → terminal invocations older than the retention     → delete
```

### 5.1 Execution ref

The workflow **body** and the code both come from the **PR head branch**
(`ref` = `refs/heads/<head branch>`). Rationale: "test this PR" semantics; a PR's
changes to its own workflow are exercised.

Two platform facts constrain this:

- The workflow file must **also exist on the default branch**, with a
  `workflow_dispatch` trigger, or the dispatch returns 404: GitHub resolves
  `{workflow_id}` against workflows registered from the default branch. A
  workflow introduced only by the PR cannot be dispatched. Slash maps this 404 to
  "workflow not registered on the default branch" rather than a raw API error.
- `workflow_dispatch` accepts a ref, not a SHA, so what executes is the branch
  tip at dispatch time. Slash shrinks the window with a pre-dispatch tip re-read
  (§5), verifies `workflow_run.head_sha` against the captured SHA after
  correlation, and notes any mismatch in the check-run summary. Tenants should
  check out `inputs.slash_head_sha` (§4.2) rather than trusting the default
  checkout.

**The load-bearing trust invariant**: because §2.4 restricts dispatch to
same-repo head branches, and GitHub only lets write+ collaborators push branches
in a repository, all executable workflow YAML is necessarily authored by a write+
user. Content trust is therefore *implied by repository mechanics*, which is why
Slash gates only on the invoking actor (§5.2) and needs no `ok-to-test`
equivalent. **This invariant evaporates the moment fork PRs are supported**, at
which point a content-trust axis (per-head-SHA maintainer grant) becomes
mandatory (§11).

Note this is *not* the same trust model as Prow, contrary to what earlier drafts
of this spec claimed. Prow gates on two independent axes (commenter trust *and*
PR-content trust via `ok-to-test`) and runs jobs on isolated, secretless
infrastructure. Slash's execution plane inherits the repository's secrets, which
is precisely why its actor gate is set at `write` and cannot be lowered (§4.1).

### 5.2 Permission model

- Gate: the comment author's repository role must be ≥ the command's `permission`
  field. Resolve via
  `GET /repos/{owner}/{repo}/collaborators/{username}/permission`.
- **Read `user.role_name`, not the top-level `permission` field.** The legacy
  `permission` field returns only `admin|write|read|none`, collapsing `maintain`
  into `write` and `triage` into `read`; using it would make a `maintain` gate
  passable only by admins. Unrecognized custom role names are mapped to the
  nearest base role via the `user.permissions` booleans, and to `none` if that
  fails.
- Default gate is `write`. `read`/`triage` are not configurable (§4.1).
- **Fail closed.** Any non-success outcome — 5xx, 403, 404, timeout, unparseable
  role — is a **deny**. Feedback is a best-effort 😕 reaction only, never a
  comment: a resolution failure means the author's trust level is *unknown*, and
  comments are reserved for authors known to be at least `read` (§6.4). A
  rate-limit condition must never become an allow — an attacker can manufacture
  one by exhausting the budget (§6.4) — and because the reaction itself passes
  the §6.4 token bucket, a manufactured resolution failure cannot be converted
  into unbounded reaction spend either (comments are already ruled out on this
  path).
- `author_association` from the webhook payload may be used **only as a cheap
  deny filter** (skip work for `NONE`/`FIRST_TIME_CONTRIBUTOR` before spending
  API calls). It must never be used as an allow: `COLLABORATOR` is returned for
  read-only collaborators and `MEMBER` for org members with no repository grant.
  Prow's hard-earned position is the same — it never uses `author_association`
  for authorization.

### 5.3 Fork and PR-state detection

`issue_comment` payloads carry no PR head information, so the PR is always
fetched (this is also how the head SHA and branch are captured). Fork status is
determined from the fetched PR: `head.repo.id != base.repo.id` is a fork, and
`head.repo == null` (deleted fork) is treated as a fork. Head information is
never inferred from the `issue_comment` payload.

Commands are accepted on draft PRs (running `/deploy staging` on a draft is
normal) and refused on `closed`/`merged` PRs: the branch is no longer under
review, its approval state is meaningless, and a reused branch name is a
ref-confusion primitive.

### 5.4 Injected inputs cannot be overridden

The `slash_` prefix is reserved in three independent places, so that no single
mistake re-opens the hole:

1. `slash-config` rejects any `args[].name` starting with `slash_` (§4.1).
2. The command parser rejects any `--slash_*` key on the command line (§3.1).
3. The dispatch input map is built **args first, injected inputs last**, using an
   insert that errors on duplicate keys rather than silently overwriting.

Why this matters: §4.2 makes `slash_head_sha` the sanctioned way for a workflow
to know what to check out. A user-supplied `--slash_head_sha=refs/pull/N/head`
would run an unreviewed fork's code inside a same-repo, full-secret run.

## 6. Checks Integration

### 6.1 Check run identity

- Name: `slash/<command>` (stable, so it can be a required status check).
- Created on the PR head SHA captured at invocation time.
- `external_id`: the invocation UUID. Treated as **public** — it is readable by
  anyone with read access and must never be relied on as a secret (§6.3).
- `details_url`: the workflow run URL, set from the dispatch response once the
  invocation correlates (§6.3). The initial `queued` check run has none — it is
  created before the POST (§5).
- Creation is idempotent: if the invocation row already carries a `check_run_id`,
  a resumed pipeline (§5) updates that check run instead of creating a second
  one. If a crash lost the id before it was persisted, the resuming worker (or
  the sweeper) looks up the App's own `slash/<command>` check run on the
  captured head SHA, adopts it and backfills `check_run_id`, rather than
  creating a duplicate.

### 6.2 Conclusion mapping

| workflow_run conclusion    | check run conclusion |
|----------------------------|----------------------|
| success                    | success              |
| failure                    | failure              |
| cancelled                  | cancelled            |
| timed_out                  | timed_out            |
| action_required            | action_required      |
| skipped / neutral / stale  | neutral              |
| startup_failure            | failure              |
| null / unknown value       | neutral, with the raw value in the summary |

Updates are monotonic: a terminal check run is never moved back to
`in_progress`, and an update to an already-reported state is skipped (§7.2).

### 6.3 Dispatch ↔ run correlation

**`POST workflow_dispatch` returns the run ID.** Passing
`return_run_details: true` yields `200` with `workflow_run_id`, `run_url` and
`html_url`; from API version `2026-03-10` this is the default response
([changelog](https://github.blog/changelog/2026-02-19-workflow-dispatch-api-now-returns-run-ids/),
[REST reference](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event)).
Slash pins `X-GitHub-Api-Version` explicitly and sends the parameter, so the
behavior holds on both versions.

Correlation is therefore **exact and authenticated by construction**:

1. Store `workflow_run_id` from the dispatch response; transition the invocation
   to `correlated` and set `details_url` on the check run.
2. Match every `workflow_run` webhook by run ID. Nothing else is matched on —
   in particular **never on `display_title`, run name, or any other
   attacker-influenceable text**. (An earlier draft correlated on a
   `slash:<uuid>` substring in `display_title`; because run names default to PR
   titles and commit messages, any outside contributor could have completed
   another user's pending check run with `conclusion: success` and bypassed
   branch protection.)
3. Verify `workflow_run.head_sha` equals the captured head SHA; on mismatch,
   proceed but note "the branch moved after the command was issued" in the
   summary.
4. Re-fetch `GET /repos/{o}/{r}/actions/runs/{id}` before writing a terminal
   conclusion, rather than trusting the webhook body.

Fallbacks, driven by the sweeper (§7.3) and never by in-process timers:

- **Missing run ID**: poll `GET /actions/runs` filtered by workflow file,
  `event=workflow_dispatch`, head branch, `triggering_actor` == the Slash App's
  bot login, and `created_at >= dispatched_at - skew`. Claim atomically —
  `UNIQUE(installation_id, owner, repo, workflow_run_id)` makes a double claim
  impossible. The `triggering_actor` predicate is what prevents claiming a run a
  human started from the Actions UI. This path is **load-bearing, not
  insurance**: an ambiguous dispatch failure (timeout or 5xx after the POST was
  sent, §7.6) leaves the invocation in `dispatched` with no response body and
  therefore no run ID, and polling is the only way to resolve it without
  risking a duplicate dispatch. API-version drift and proxies stripping the
  response body land in the same recovery path.
- **Lost webhooks**: an invocation in `correlated` past its deadline is resolved
  by polling the run directly. An invocation `dispatched` for more than 10
  minutes is closed out by the same polling, to one of two terminal states
  (§7.2): the polls succeeded and no matching run exists → `dispatch_failed`;
  the run's existence is still undeterminable (polling errors) →
  `correlation_timeout`. Both complete the check run `completed/failure` with
  the respective explanation.
- **Run never terminates** (webhook outage, run wedged): a max-runtime deadline
  (default 72h, matching GitHub's own workflow cap) marks the check run
  `completed/timed_out`. Without this the check run sits `in_progress` forever
  and the invocation row is immortal.

The `run-name: "slash:${{ inputs.slash_run_id }}"` convention from earlier drafts
is **no longer required for correlation**. Tenants may still set a `run-name` for
readable run titles; Slash does not read it.

### 6.4 User feedback channels

- 🚀 reaction on the triggering comment: command accepted.
- 😕 reaction + a PR comment: any user-correctable failure (bad args with a usage
  block, permission denied, config error, fork PR, PR not open, misplaced
  command). The one exception is a failed permission *resolution* (§5.2):
  😕 only, no comment, because the author's trust level is unknown.
- Check run summary: execution status, link, timing, actor, and the original
  command line. Never spam extra comments for normal lifecycle progress — the
  check run is the status surface.

Anti-spam rules, which override the "never silently dropped" principle where they
conflict:

- **Unknown commands do not generally get a reply.** The gate into the pipeline
  is only "first line starts with `/`", which `/etc/nginx.conf is wrong`,
  `/cc @alice` (Prow muscle memory) and `/api/v2 returns 500` all satisfy. Prow
  and Lighthouse never reply to unrecognized slash text, and an org-wide bot that
  does is an adoption risk. Slash replies with the command list only when the
  first token is a syntactically valid command name with nothing suspicious after
  it **and** either it is within edit distance 2 of a configured command, or the
  repository has no commands configured at all (the "installed but not
  configured" case, §8). Otherwise: no comment, no reaction.
- **Comments require a trusted actor.** *Every* comment Slash posts — usage
  errors, permission denied, config errors, fork and not-open notices,
  command-not-found and misplaced-command replies — requires the author to have
  resolved to at least `read`; the permission resolution happens first in §5's
  ordering. Authors resolving below `read`, and authors whose permission cannot
  be resolved, get at most the 😕 reaction (§5.2).
- **Deduplication.** Slash never posts a comment identical to one it already
  posted on the same PR for the same cause. The fork explanation, the
  not-configured notice, and the misplaced-command notice are posted at most once
  per PR.
- **Budget.** All mutating GitHub calls — reactions included — pass a token
  bucket per `(installation, repo, actor)` and per `installation`. On
  exhaustion, comments are suppressed first (degrading to reaction-only), then
  reactions too (degrading to silence); every suppressed call is recorded in
  metrics, and all feedback is best-effort. The rate limit is per
  *installation*, so without this one attacker on one public repo would degrade
  Slash for every repository in that org.
- **Escaping.** Every interpolated user value passes through one
  `escape_user_text()` helper: control characters and newlines stripped,
  hard-truncated to 200 characters, wrapped in a code fence longer than any
  backtick run it contains. Check-run summaries and comments render Markdown and
  a subset of HTML, and they carry the Slash App's trusted identity — raw
  attacker text there is a phishing surface.

### 6.5 Re-run

GitHub renders a "Re-run" affordance on App-created check runs and delivers
`check_run.rerequested` to the creating App. Slash subscribes and implements it:
load the stored invocation, re-resolve the **rerequester's** permission against
the command's current `permission` (never the original invoker's), re-capture the
PR head, and claim a **fresh invocation row** for the same comment with the next
`attempt` (§7.2) — the original row stays terminal — then run the normal pipeline
from the claim onward (new check run, dispatch). If the rerequester's permission
cannot be resolved, the re-run is denied fail-closed (§5.2); no comment surface
exists here, so the rerequest is dropped and recorded in metrics. A stale or
unknown `check_run_id` is answered by completing the check run with an
explanation.

This delivers the `/retest`-shaped feature that makes required status checks
usable (§6.6) at a fraction of the cost of a built-in command, and avoids
shipping a visibly dead button on Slash's own primary status surface.

### 6.6 Required status checks: capability and footgun

`slash/<command>` is a stable check-run name, so branch protection can require
it. Two consequences must be understood before doing so, and both are documented
prominently in the user docs:

- **A PR where nobody runs the command never becomes mergeable.** The required
  check stays `Expected` forever.
- **Every push resets it.** Required checks are evaluated on the head commit, and
  Slash creates check runs only on the SHA captured at invocation. After a push,
  the command must be re-issued (the Re-run button of §6.5 makes this one click).
  Prow avoids this by re-running presubmits on `synchronize`; Slash 0.0.1
  deliberately does not (§2.4, §11).

Marking `slash/<cmd>` required is therefore appropriate either for commands the
team runs on every PR revision, or as a deliberate manual merge gate — not as a
default.

### 6.7 Concurrent invocations of the same command

Check runs are named per command, and GitHub's PR UI and branch-protection
evaluation surface only the latest check run of a given name on a SHA. So
`/deploy staging` and `/deploy production` in flight together on the same head
SHA would mask each other.

0.0.1 semantics: **latest wins, explicitly.** Creating an invocation for
`(repo, pr, command)` moves older non-terminal invocations of the same triple to
the terminal state `superseded` and stops updating their check runs, so a late
`workflow_run` event for an older run cannot resurface stale status. The older
workflow run is *not* cancelled. Superseding writes one final update to the old
check run — `completed`/`neutral`, with a summary recording that it was
superseded and linking the newer run — so a superseded check run never stays
`in_progress`.

Renaming check runs per argument set would fix the masking but break the stable
name that makes required status checks possible, so it is rejected.

## 7. Architecture

### 7.1 Stack

- Language: **Rust** (stable toolchain).
- HTTP: `axum` + `tokio`; GitHub client: `octocrab`.
- Persistence: **PostgreSQL** via `sqlx`, from day one. Postgres-only, not
  abstracted over SQLite: the design depends on `FOR UPDATE SKIP LOCKED` (§7.3),
  and an abstraction layer would trade sqlx's compile-time-checked queries for
  lowest-common-denominator SQL.

  **Decision record (2026-08-03).** Two lighter alternatives were evaluated for
  faster idea validation and rejected:

  - *No database*: viable only as a throwaway spike. The idempotency claim must
    be durable **before** the irreversible `workflow_dispatch` (which has no
    idempotency key, §7.6), and the Checks API offers neither create-if-absent
    nor conditional update, so GitHub itself cannot serve as the invocation
    record: a redelivery racing an in-flight request double-dispatches (§10,
    criterion 5), a crash between check-run creation and dispatch loses the
    command, a crash after dispatch leaves the check run permanently
    non-terminal (§10, criterion 6), and an ambiguous dispatch outcome is
    unresolvable without a durable `dispatched` state. The prow precedent does
    not transfer — prow's
    one-record design rests on etcd's atomic create and `resourceVersion`
    compare-and-swap, primitives the Checks API lacks.
  - *SQLite first, Postgres later*: feasible in a single process (the
    correctness core is plain transactions, unique constraints, and guarded
    updates), but the engine swap rewrites exactly the consumption/sweeper
    layer that is the structural heart of §7.3, re-verifying all concurrency
    behavior on a new engine with no dogfood soak — while saving only the
    minutes it takes to run Postgres via `docker-compose` or a free hosted
    instance. It is slower to a first live demo than building on Postgres
    directly.

  Speed of validation is bought by shrinking scope, never by changing the
  database.
- Config: environment variables (`SLASH_GITHUB_APP_ID`,
  `SLASH_GITHUB_PRIVATE_KEY_PATH`, `SLASH_WEBHOOK_SECRET`, `SLASH_DATABASE_URL`).
  The private key is read from a **file** (mode 0400), not passed inline in the
  environment, and the config struct does not implement `Debug`.
- Deployment: stateless containers + Postgres. The 0.0.1 **reference deployment
  is a single replica**: at n = 1 there is no cross-replica contention on
  `FOR UPDATE SKIP LOCKED` (the in-replica worker pool still exercises it), so
  scale-out is a deployment change, not a code change. Horizontal
  scale-out is safe because every piece of coordination lives in the database
  (§7.3) — there is no in-process timer or queue whose loss changes an
  outcome — and race-freedom is proven by the plan's two-worker concurrency
  tests rather than by running multiple replicas in production.

### 7.2 State

The design follows Prow and Lighthouse in the one respect that matters most: a
**durable record plus level-triggered reconciliation**, rather than replaying
edge-triggered events. Prow's `crier` does not replay events; it reconciles the
current state of the `ProwJob` record. Postgres is Slash's `ProwJob`.

Table `deliveries` — the transactional inbox (§7.3):

| column        | notes                                              |
|---------------|----------------------------------------------------|
| delivery_guid | PK, from `X-GitHub-Delivery`                       |
| event, payload| raw bytes as received                              |
| received_at, state, attempts, last_error | `pending`/`done`/`failed` |

Table `invocations`:

| column                | notes                                            |
|-----------------------|--------------------------------------------------|
| id (uuid)             | = `slash_run_id`                                 |
| installation_id, owner, repo | tenancy                                    |
| comment_id, attempt   | **UNIQUE with installation_id** — the idempotency key. The §5 comment path claims attempt 1; each re-run claims the next attempt (§6.5) |
| pr_number, head_sha, head_branch |                                       |
| actor, actor_id       | needed by §4.2 and the §6.4 summary              |
| command, raw_comment_line, args (jsonb) |                                |
| check_run_id          |                                                  |
| workflow_file         |                                                  |
| workflow_run_id       | nullable until correlated; **UNIQUE with (installation_id, owner, repo)** |
| status                | `claimed` → `dispatched` → `correlated` → `completed`, plus terminal `aborted`, `dispatch_failed`, `correlation_timeout`, `superseded` (lifecycle below) |
| conclusion            | the §6.2 outcome, distinct from lifecycle status |
| failure_reason        | human-readable detail for the check-run summary  |
| last_reported_status  | Prow's `PrevReportStates` analog; makes check-run updates idempotent and monotonic |
| created_at, dispatched_at, correlated_at, completed_at, deadline_at | drive the sweeper and the summary's duration |
| dispatch_attempts     | observability for §7.6                           |

Invocation lifecycle — every outcome in §5, §6.3 and §8 maps to exactly one
status:

- `claimed` — the row exists (the §5 idempotency claim); the pre-dispatch steps
  (reaction, check run, supersede, tip re-read) may be incomplete. The POST has
  **not** been sent: the transition to `dispatched` is written **before** the
  POST (write-ahead), so a crash can never leave a row whose dispatch status is
  unknowable. A `claimed` row stranded by a crash is resumed by its
  still-`pending` delivery (§5, §7.3); if it cannot be driven forward, the
  sweeper collects it into `aborted`.
- `dispatched` — the POST may have been sent. Ambiguous outcomes (§7.6) stay
  here; resolved by the §6.3 fallbacks, never by re-POSTing.
- `correlated` — run ID known; awaiting the run's terminal event.
- `completed` — terminal; `conclusion` carries the §6.2 outcome. A run that
  never terminates ends here with conclusion `timed_out` via the 72h deadline
  (§6.3).
- `aborted` — terminal, pre-dispatch: the head moved before dispatch (§5, §8),
  or a stranded `claimed` row was swept. No workflow run exists. Entering
  `aborted` completes the invocation's check run, if one was created — found by
  stored `check_run_id` or by head-SHA lookup (§6.1) — with "re-issue the
  command".
- `dispatch_failed` — terminal: permanent dispatch failure (404/422, §7.6), or
  no run ID resolvable within 10 minutes of an ambiguous dispatch when polling
  confirms no run was created.
- `correlation_timeout` — terminal: `dispatched` past the 10-minute resolution
  deadline with the run's existence still undeterminable (§6.3).
- `superseded` — terminal: replaced by a newer invocation of the same
  `(repo, pr, command)` (§6.7).

Table `installations`: installation id, account, `state`
(`active`/`suspended`/`deleted`), updated by `installation*` webhooks **and** by
the 401 path (§7.5), so the signal does not depend on a webhook being delivered
at all — GitHub does not redeliver webhooks (§7.3).

State transitions are **guarded compare-and-swap** statements
(`UPDATE ... WHERE id = $1 AND status IN (...)`); zero rows updated means the
event is stale or duplicate and is dropped. Terminal states absorb everything.
Check-run API calls are derived from the post-transition database state, never
directly from a webhook payload. This is what makes out-of-order delivery
(`completed` before `in_progress`) and manual redelivery harmless — GitHub gives
no ordering guarantee.

Retention: terminal invocations are deleted after 30 days by the sweeper.
Non-terminal rows are **never** deleted on age alone — they are first driven
through their timeout transition so the check run gets a terminal update, and
only then collected (Prow's `sinker` invariant).

### 7.3 Webhook endpoint and durability

`POST /webhook`:

1. Read the **raw body bytes** (`Bytes`, with an explicit request-body limit);
   JSON is parsed only after verification.
2. Require `X-Hub-Signature-256`, the `sha256=` prefix, `X-GitHub-Event`,
   `X-GitHub-Delivery`, and `content-type: application/json`; 403 if the
   signature header is absent. The legacy SHA-1 `X-Hub-Signature` is never
   honored. Comparison is constant-time over the exact received bytes. If
   `SLASH_WEBHOOK_SECRET` is unset the process refuses to start — verification is
   never skipped.
3. `INSERT INTO deliveries` (PK on the delivery GUID, so a redelivery is a no-op)
   and return 200. **This is the durability boundary**: only after the row is
   committed is the delivery acknowledged.
4. Workers consume with `SELECT ... FOR UPDATE SKIP LOCKED` and mark the delivery
   `done` only after the pipeline's side effects complete.

Why this rather than the "enqueue in-process, return 200 fast" of earlier drafts:
**GitHub does not automatically redeliver webhooks** — not on failure, and
certainly not after a 200. A crash between the 200 and the end of the pipeline
loses the command permanently, and the worst window is between creating the
check run on GitHub and persisting its id on the already-claimed invocation
row, which would leave a check run that is never updated — permanently blocking
any PR that requires it. The pending-delivery resume (§5) and the sweeper's
head-SHA lookup (§6.1) close exactly this window.

The **sweeper** runs on every replica on an interval, doing the work listed at
the end of §5. It uses `FOR UPDATE SKIP LOCKED` for coordination, so multiple
replicas need neither leader election nor a scheduler component, and no timeout
depends on the process that started the work still being alive.

Events subscribed: `issue_comment`, `workflow_run`, `check_run`, `installation`,
`installation_repositories`, `pull_request`.

- `check_run` powers §6.5.
- `pull_request` is used for exactly one thing in 0.0.1: on `synchronize`, record
  the new head SHA on the PR's open invocations so the summary can say "the
  branch moved after this command was issued". It does **not** re-trigger
  anything (§2.4).

Other endpoints: `GET /healthz` (liveness/readiness), `GET /metrics` (§7.4).

### 7.4 Observability

The dominant failure modes of this architecture are silent by construction, and
the Definition of Done requires a latency percentile that cannot otherwise be
measured. A Prometheus `/metrics` endpoint ships in 0.0.1 with:

- `slash_webhook_deliveries_total{event,outcome}` and a handler latency histogram
- `slash_deliveries_pending` (inbox depth) and oldest-pending age
- `slash_invocations{status}` and **max age in `dispatched`** — the stuck-invocation alarm
- `slash_correlation_total{path}` — `dispatch_response` vs `polled` vs `timeout`
- `slash_github_api_calls_total{endpoint,status}` and rate-limit-remaining per installation
- `slash_dispatch_failures_total{class}`, `slash_comments_suppressed_total{reason}`

### 7.5 GitHub App and credentials

Permissions: `checks: write`, `actions: write`, `contents: read`,
`pull_requests: write`, `issues: write`, `metadata: read`.

`issues: write` is **required, not optional**: subscribing to `issue_comment`
needs at least `Issues: read` ("To subscribe to this event, a GitHub App must
have at least read-level access for the Issues repository permission"), and
creating a reaction on a PR comment — a PR comment *is* an issue comment — needs
`Issues: write`. Without it the App receives no comment events at all and the
product does not function. Earlier drafts omitted it.

Installation tokens are minted **per repository with least permissions**
(`repositories` + `permissions` on the token-mint call), cached keyed by
`(installation_id, repo_id, permission_set)`. This bounds a leaked token to one
repository and one verb instead of every tenant repository the App is installed
on. On a 401, the cached token is invalidated and re-minted once; if the re-mint
404s the installation is marked `deleted` in Postgres and its queued work is
abandoned cleanly.

Operational requirements: an audit record of every dispatch (installation, repo,
PR, actor, command, workflow, ref, resulting run id) written *before* the API
call; a per-installation and global kill switch checked before every mutating
call; key rotation and incident procedure documented in the deployment notes.

### 7.6 Retry policy

`workflow_dispatch` is not idempotent and has no idempotency key, so a blind
retry of an ambiguous failure launches a second run.

- Retry only failures known **not** to have reached GitHub: connection failures,
  and 429/secondary-rate-limit with `Retry-After`.
- Treat ambiguous outcomes (request timeout, 5xx after the body was sent) as
  *possibly dispatched*: leave the invocation in `dispatched` and let the sweeper
  resolve it by polling. Never re-POST.
- Never retry 401/403-auth or 422; those are permanent and get a user-facing
  message — except a 403 from permission resolution, where §5.2 applies (deny,
  best-effort 😕, no comment).
- Read-after-write 404s (fetching a PR immediately after its comment event,
  polling for a run dispatched milliseconds ago) get a small bounded retry.
- 403 with `RateLimit-Remaining: 0` sleeps until reset; `Retry-After` is honored;
  every wait is capped so a worker cannot hang.
- Updating a check run on a captured SHA can 404/422 after a force-push or branch
  deletion. That class is permanent — record it and stop, never spin.

## 8. Failure & Edge Cases (must-handle)

- Comment on an issue (not PR) → ignore silently.
- Comment whose first line is not a command → ignore silently, zero API calls.
- `/cmd` with no `.slash/` directory → "installed but not configured" comment
  (once per PR), per the §6.4 rules.
- Malformed YAML in `.slash/` → comment with file + parse error; resource limits
  exceeded → comment naming the limit.
- Duplicate command across files → comment naming both files.
- Workflow file missing from the default branch, or lacking `workflow_dispatch`
  → 404/422 mapped to a specific explanation (§5.1) plus check run `failure`.
- Configured arg not declared in the workflow → caught before dispatch (§4.2)
  with a precise message instead of a 422.
- PR not open → comment, no dispatch. Fork PR → fork comment, once per PR.
- PR head SHA changes between comment and dispatch → abort (terminal status
  `aborted`) with "the PR head moved, re-issue the command" (§5). Changes
  *after* dispatch → run proceeds, and the summary notes the mismatch (§6.3).
- Required check + command never invoked → stays `Expected`; documented, not a bug (§6.6).
- Required check + push after success → must be re-issued; the Re-run button
  covers it (§6.5, §6.6).
- Concurrent same-command invocations → older ones `superseded` (§6.7).
- Webhook redelivery (always manual) → no-op via the `deliveries` PK and the
  `(installation_id, comment_id, attempt)` unique constraint (§7.2).
- Out-of-order or duplicate `workflow_run` events → dropped by the guarded
  transitions (§7.2).
- Dispatch ambiguous failure → sweeper resolves; no double dispatch (§7.6).
- Rate limits → §7.6 plus the §6.4 token bucket.
- Author permission cannot be resolved (5xx/403/404/timeout/unparseable role) →
  deny; best-effort 😕 reaction through the token bucket; never a comment
  (§5.2, §6.4).
- Installation suspended/uninstalled → tokens invalidated, queued work abandoned (§7.5).
- Run never terminates → 72h deadline → `timed_out` (§6.3).

## 9. Engineering Conventions

- **English is the working language** for all code, comments, commits, docs,
  and issues.
- `rustfmt` + `clippy -D warnings` enforced in CI; `cargo test` green on every
  commit; conventional commits.
- All user-facing strings (comments, check summaries) live in one module for
  consistency of voice, and every user value interpolated into them goes through
  `escape_user_text()` (§6.4).
- No panics reachable from untrusted input (webhook bodies, comment text, YAML):
  handlers are panic-guarded, and the parsing surfaces carry property/fuzz tests.
- Untrusted input surfaces have explicit size limits at the edge: request body,
  comment line length, `.slash/` bytes and file count, serialized inputs payload.

## 10. Success Criteria (0.0.1)

Measured on a real test repository, with numbers so the result is falsifiable:

1. **Happy path, 20 invocations of `/echo hello --loud`**: 🚀 reaction and a
   `slash/echo` check run visible at p95 ≤ 10s after the comment; 20/20 reach a
   terminal conclusion matching the workflow outcome, with a working run link.
2. **Correlation**: 20/20 correlate via the dispatch response (`slash_correlation_total{path="dispatch_response"}`),
   with no workflow `run-name` configured anywhere.
3. **Permission**: a user with read access gets a permission-denied comment and
   no dispatch; a user with `NONE` association gets no comment at all.
4. **Argument validation**: an invalid `choices` value yields a usage comment and
   no dispatch; `--slash_head_sha=...` is rejected as a usage error.
5. **Idempotency**: manually redelivering the `issue_comment` delivery produces
   no second check run and no second workflow run.
6. **Durability**: killing the replica immediately after dispatch still results
   in the check run reaching a terminal conclusion once the replica restarts —
   the sweeper resumes from durable state (§7.3). Multi-replica race-freedom is
   proven by the plan's two-worker concurrency tests, not by this criterion;
   the 0.0.1 reference deployment is a single replica (§7.1).
7. **Re-run**: clicking Re-run on a completed `slash/echo` check run dispatches a
   new run and updates the check run.
8. **Branch protection**: with `slash/echo` required, a PR is unmergeable until
   the command succeeds, becomes mergeable after success, and returns to
   `Expected` after a subsequent push (documented behavior, §6.6).
9. **Multi-tenancy**: the above holds with two installations active
   simultaneously, and no cross-tenant leakage appears in the audit log.
10. **Quiet by default**: comments such as `/etc/passwd is wrong` and
    `/cc @someone` on a configured repository produce no bot reply.

## 11. Known Limitations and Roadmap

Documented in the user docs so first contact is not a surprise:

- **Fork PRs are unsupported** — a GitHub platform limitation
  (`workflow_dispatch` cannot target a fork ref), not user error. Workaround: a
  maintainer pushes the branch to the base repository. Supporting forks requires
  a content-trust axis: a per-head-SHA, maintainer-issued, revocable grant
  (Prow's `ok-to-test`, but re-required on every push because Slash's execution
  plane carries repository secrets), likely combined with approving
  `pull_request`-triggered runs rather than dispatching. Prow already bridges to
  GitHub Actions this way with the same `actions: write` permission Slash holds.
- **No automatic re-trigger on push** — the single most requested thing that
  would make required status checks comfortable; the Re-run button (§6.5) is the
  0.0.1 substitute.
- **Concurrent same-command runs mask each other** in the PR UI (§6.7).
- **No server-side `.slash/` validation on push** — the person who breaks the
  config on the default branch is not the person who sees the error, possibly
  days later. `slash validate` in tenant CI covers this for 0.0.1; a
  `slash/config` check run on push is the planned fix.
- **No shared defaults across command files** (e.g. a repo-wide permission
  floor); a future `slash.yml` may add them.
- **Commands must be on the first line** of a comment (§3.2).
