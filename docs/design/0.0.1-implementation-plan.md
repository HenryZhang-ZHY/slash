# Slash 0.0.1 — Implementation Plan

Companion to [`0.0.1-spec.md`](./0.0.1-spec.md). The spec is the source of
truth; this document sequences the work. Intended executor: an autonomous
coding agent. Work milestone by milestone; each milestone ends with green CI
and its listed exit criteria met before the next begins.

Revision 2 (2026-08-03) reflects the design review: a correlation spike moves to
the front, M4 builds a durable inbox and sweeper instead of an in-process queue,
metrics ship with the server rather than being deferred, and dogfooding starts at
M5 instead of at the end.

Revision 3 (2026-08-03) records the persistence decision — PostgreSQL from day
one, single-replica reference deployment; no-database and SQLite-first were
evaluated and rejected (spec §7.1) — moves the local Postgres `docker-compose.yml`
up from M7 to M4, makes M5 slice demo-first so the first live invocation lands
as early as possible, and folds the spec's completed invocation lifecycle
(write-ahead dispatch, stale-`claimed` sweep — spec §7.2) into M6's scope.

## Repository Layout

```
slash/
├── Cargo.toml                 # workspace
├── crates/
│   ├── slash-server/          # bin: axum app, webhook endpoint, workers, wiring
│   ├── slash-cli/             # bin `slash`: `slash validate .slash/`
│   ├── slash-github/          # GitHub App auth, octocrab wrappers, API types
│   ├── slash-command/         # command-line lexer/parser (pure, no IO)
│   ├── slash-config/          # .slash/*.yml schema, parsing, validation (pure)
│   └── slash-core/            # domain: invocation state machine, correlation,
│                              #   check-run lifecycle, user-facing messages
├── migrations/                # sqlx migrations
├── docs/
│   ├── design/                # this folder
│   └── user/                  # user-facing docs (written in M7)
├── examples/                  # example .slash/ + workflow for the test repo
├── fixtures/                  # real recorded webhook payloads (from M0.5)
└── .github/workflows/ci.yml
```

Pure crates (`slash-command`, `slash-config`, and the logic in `slash-core`) must
be testable without network or database. IO lives at the edges
(`slash-server`, `slash-github`).

## Milestones

### M0 — Scaffold
- Cargo workspace with the crates above (empty libs), rustfmt config,
  `clippy -D warnings`, CI workflow (fmt + clippy + test, with a Postgres
  service), LICENSE (MIT, already in the repository), `.gitignore`.
- Exit: CI green on an empty workspace.

### M0.5 — Correlation spike (live GitHub, no Slash code required)

The riskiest assumptions in the spec are empirical GitHub behaviors, and they are
cheap to settle now and expensive to discover at M6. A scratch repository, `curl`
(or `gh api`), and a webhook capture (`smee.io`) answer all of it in well under a
day. Nothing here depends on M0–M5.

Questions to settle, each recorded as a note plus the raw payloads:

1. `POST .../dispatches` with `return_run_details: true` on
   `X-GitHub-Api-Version: 2022-11-28`, and without the flag on `2026-03-10`:
   confirm 200 and the `workflow_run_id`/`run_url`/`html_url` body (spec §6.3).
   Confirm `octocrab` can surface it; if not, note the raw-request workaround.
2. Which version of the workflow file GitHub validates `inputs` against — the
   default-branch registration or the dispatched ref (spec §4.2). Test by
   declaring an input only on the head branch.
3. `workflow_run` delivery: which of `requested`/`in_progress`/`completed` fire,
   in what order, with what latency, and whether `run_started_at`/`created_at`
   are usable for durations.
4. HTTP 422 shape for undeclared inputs, and 404 shape for a workflow that exists
   only on the head branch (spec §5.1, §8).
5. `GET /collaborators/{u}/permission` response for `triage` and `maintain`
   collaborators, confirming `role_name` is the only faithful field (spec §5.2).
6. That `issues: write` is required to receive `issue_comment` and to add a
   reaction — install with and without it (spec §7.5). **This is the assumption
   whose failure mode is "the product receives nothing".**
7. `check_run.rerequested` payload from clicking Re-run on an App check run
   (spec §6.5).
8. Whether the native GitHub Actions check runs for a dispatched run appear on
   the PR alongside `slash/<command>`, and how a same-named check run on the same
   SHA behaves for branch protection (spec §6.7).

- Exit: `fixtures/` contains the real payloads, `docs/design/0.0.1-spike-notes.md`
  records each answer, and any spec correction is applied before M1 starts.

### M1 — Command parser (`slash-command`)
- Lexer/parser for the grammar in spec §3: command name (case-insensitive),
  positionals, `--key=value`, `--key value`, boolean flags, double-quote quoting
  with escapes. First-line-only extraction, plus the §3.2 scan of remaining lines
  against a supplied set of configured command names.
- Reject `--slash_*` keys (§3.1, §5.4) and values failing the §3.1 charset, with
  typed errors carrying human-readable positions.
- Exit: exhaustive unit tests incl. property tests (`proptest`) for
  quoting/escaping round-trips; malformed input never panics; a fuzz-style
  property test that no input produces a `--slash_*` key in the output.

### M2 — Config (`slash-config`) + `slash validate`
- serde model for spec §4.1 with `deny_unknown_fields`; a maintained YAML crate
  (`serde_yaml` is archived — evaluate `serde_yaml_ng`/`serde_norway` and record
  the choice) with aliases/anchors disabled and the §4.1 resource limits enforced
  before parsing.
- Validation: duplicate commands (naming both files), reserved command names
  (`help`, `slash`), `permission` restricted to `write|maintain|admin`,
  `workflow` filename pattern, `args[].name` pattern + `slash_` prefix rejection
  + uniqueness, required-before-optional positional rule, `default` rejected on
  required entries and validated against `choices`/charset, ≤ 25 total inputs.
- Binder: parsed command line + config → validated input map, or a typed
  validation error that renders as a usage block. Enforces the §3.1 value charset
  with the `free_text` opt-out, and the 65,535-character payload cap.
- `slash-cli`: `slash validate [path]` exits non-zero and prints every error,
  suitable for tenant CI (spec §2.3).
- Exit: unit tests covering every validation rule and binding case (defaults,
  choices, missing required, unknown key, reserved prefix, oversize directory,
  YAML bomb); `slash validate` tested against fixture directories.

### M3 — GitHub plumbing (`slash-github`)
- App JWT signing (private key read from a file); **per-repository,
  least-permission** installation tokens with a cache keyed by
  `(installation_id, repo_id, permission_set)` and the 401 invalidate-and-remint
  path (spec §7.5).
- Webhook signature verification per spec §7.3: raw bytes, required headers,
  `sha256=` only, constant-time compare, explicit body limit.
- The retry/backoff ladder of spec §7.6 as middleware, with the permanent-vs-
  transient-vs-ambiguous classification exposed in the error type — callers must
  be able to distinguish "definitely not dispatched" from "possibly dispatched".
- Thin typed wrappers used by core: get PR, get collaborator permission (reading
  `role_name`), get repository content (`.slash/` listing + file fetch, and the
  workflow file at a ref), create/update check run, create comment, create
  reaction, dispatch workflow (**with `return_run_details`, returning the run
  id**), get workflow run, list workflow runs.
- Exit: unit tests with mocked HTTP (`wiremock`); signature verification test
  vectors; the M0.5 fixtures parsed by the typed payload structs; a test per
  retry classification.

### M4 — Server, durability, observability (`slash-server`)
- axum app: `POST /webhook` implementing the spec §7.3 sequence — verify raw
  bytes → `INSERT INTO deliveries` → 200. `GET /healthz`, `GET /metrics`.
  Graceful shutdown, tracing with the delivery GUID on every log line,
  panic-guarded handlers.
- Postgres via sqlx; migrations for `deliveries`, `invocations`, `installations`
  (spec §7.2) including every unique constraint.
- Local Postgres lands here, not at M7: a minimal `docker-compose.yml` with a
  single `postgres` service (M7 extends it into the full local-dev setup). Where
  Docker Desktop is unavailable (e.g. a corporate Windows machine), a free
  hosted Postgres (Neon, Fly) supplied via `SLASH_DATABASE_URL` /
  `SLASH_TEST_DATABASE_URL` is the supported fallback — provisioning the
  database must never become the schedule bottleneck.
- Worker pool consuming `deliveries` with `FOR UPDATE SKIP LOCKED`; the
  **sweeper** skeleton (spec §7.3): interval loop, claiming, retention GC. The
  invocation-facing duties (stale-`claimed` collection, `dispatched`/
  `correlated` deadlines, failed-update retry) land in M6, once invocations
  exist.
- Prometheus metrics per spec §7.4.
- Refuse to start without `SLASH_WEBHOOK_SECRET`; config struct without `Debug`.
- Postgres-backed tests are gated on `SLASH_TEST_DATABASE_URL` and skip cleanly
  when it is absent (e.g. before a local or hosted database is provisioned); CI
  always sets it.
- Exit: integration tests posting signed sample payloads (M0.5 fixtures)
  end-to-end into a test DB; a redelivery test asserting a single `deliveries`
  row; a test that killing a worker mid-pipeline leaves the delivery `pending`
  and a second worker completes it.

### M5 — Dispatch pipeline (`slash-core` + wiring)
- **Slice demo-first.** Implement the spec §5 happy path for a single command
  (`/echo`) end-to-end before broadening: webhook → claim → 🚀 → check run
  `queued` → dispatch → run ID stored. Dogfood that thin slice on a real PR
  first, then fill in the full decision tree, the §6.4 suppression rules, and
  the failure paths. The point of 0.0.1 is to validate the idea, and the thin
  slice *is* the validation — everything after it hardens a demo that already
  works.
- Full happy path of spec §5 in the specified **guard order** (trust before any
  user-visible side effect), up to and including `workflow_dispatch`: PR fetch,
  open/fork checks, config load with SHA-keyed cache, permission gate (fail
  closed, `role_name`), parse/bind, invocation claim on
  `(installation_id, comment_id)`, 🚀 reaction, check run `queued`, supersede,
  pre-dispatch tip re-read, workflow-file input introspection, dispatch.
- All user-facing strings in one module, all user values through
  `escape_user_text()`; the §6.4 anti-spam rules (edit-distance reply gate,
  trusted-actor requirement, per-PR dedup, token bucket).
- Every user-correctable failure path emits the correct comment/reaction; API
  failure paths mark the check run `failure` with a mapped explanation.
- **Dogfooding starts here**: a staging deployment is installed on the `slash`
  repository itself with `.slash/echo.yml`, and the command is invoked on a real
  PR. From this milestone on, invoking it is part of the PR ritual — every
  subsequent PR becomes a free end-to-end test.
- Exit: integration tests with mocked GitHub covering the §5 decision tree
  exhaustively (each rejection branch + happy path), the §6.4 suppression rules,
  and the reserved-input attacks of §5.4; dogfood invocation succeeded on a real PR.

### M6 — Correlation & status sync
- `workflow_run` handler: exact match by run id, guarded CAS transitions,
  monotonic check-run updates via `last_reported_status`, head-SHA verification,
  re-fetch before writing a terminal conclusion, §6.2 mapping, summary content
  (run link, duration, actor, original command line).
- Sweeper paths: missing-run-id polling with the `triggering_actor` predicate and
  atomic claim, lost-webhook polling, 10-minute dispatch timeout, 72h run
  deadline, failed-update retry, stale-`claimed` collection (crash before the
  POST → `aborted`, spec §7.2).
- `check_run.rerequested` handler (spec §6.5), re-gating on the rerequester.
- `pull_request.synchronize` recording the moved head SHA (spec §7.3).
- Exit: integration tests for exact match; missing-run-id polling recovery;
  a human-started run of the same workflow on the same branch is **not** claimed;
  `completed` before `in_progress`; duplicate `completed`; stale event after a
  terminal state; superseded invocation stops updating; run never terminates →
  `timed_out`; a worker killed between claim and dispatch → the row is swept to
  `aborted` and the check run reaches a terminal state; rerequested by a user
  who no longer has permission → denied;
  the two-worker concurrency tests of the Testing Strategy (claim, supersede,
  sweeper against one Postgres) — the race-freedom proof that spec §7.1 and
  §10 criterion 6 delegate to this plan.

### M7 — Ship
- Dockerfile (slim/distroless); extend the M4 `docker-compose.yml` into the full
  local-dev setup (server + Postgres); deployment notes including key rotation,
  the incident procedure (spec §7.5), and the single-replica reference
  deployment (spec §7.1).
- `docs/user/`: getting started, `.slash/` reference, workflow requirements
  (injected inputs, the `env:`-not-`${{ }}` security rule), permissions,
  **required-status-check caveats (spec §6.6)**, and limitations (spec §11).
- `examples/`: a working `.slash/echo.yml` + `.github/workflows/echo.yml` pair,
  written to be a safe copy-paste starting point.
- Manual E2E against the spec §10 success criteria.
- Exit: spec §10 demonstrated end-to-end; tag `v0.0.1`.

Dependency order: M0 → M0.5 (independent of all code) → M1 ∥ M2 ∥ M3 → M4 →
M5 → M6 → M7.

## Testing Strategy

- Unit tests: all parsing/validation/state-machine logic (pure crates).
- Integration tests: axum server + mocked GitHub (`wiremock`) + real Postgres;
  fixtures are the **real recorded payloads from M0.5**, not hand-written guesses.
- Concurrency tests: two workers/replicas against one Postgres to prove the
  claim, supersede, and sweeper paths are race-free.
- E2E: the dogfooding loop from M5 onward, plus the scripted M7 checklist.
- Every bug found in E2E gets a regression test at the lowest possible layer.

## Definition of Done (release checklist)

- [ ] All spec §10 success criteria pass on a live test repository, with numbers.
- [ ] All spec §8 edge cases have automated coverage.
- [ ] CI: fmt, clippy (`-D warnings`), unit + integration tests green.
- [ ] Webhook handler p99 response < 1s under a redelivery burst, **measured from
      the `/metrics` histogram**.
- [ ] Killing a replica at any pipeline step leaves no check run permanently
      non-terminal (verified for the dispatch and correlation steps).
- [ ] Two-worker concurrency tests (claim, supersede, sweeper) green — the
      race-freedom proof backing spec §7.1's scale-out claim.
- [ ] User docs sufficient for a stranger to onboard without help, including the
      required-status-check caveats.
- [ ] No panics reachable from untrusted input (webhook bodies, comments, YAML)
      — fuzz or property tests on those surfaces.
- [ ] Security review of the §5.4 reserved-input defenses, the §6.4 escaping, and
      the §5.2 fail-closed paths, each with a test that fails if the defense is removed.

## Deliberately Deferred (do not build in 0.0.1)

Fork PR support, automatic re-trigger on `synchronize`, server-side `.slash/`
validation on push, multi-workflow commands, aliases, built-in chat commands
(`/retest`, `/help`), org-level config and shared defaults, GH Enterprise,
dashboard, billing. See spec §2.4 and §11.
